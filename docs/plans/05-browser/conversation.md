# CHATUI · Read a native conversation and send to its lead

**Acceptance needs SHELL and REPORT.** Start after SHELL on the [first working review](../01-foundation/first-review.md) with feature fixtures. Use the [native reader](../02-sessions/history.md) and [host adapters](../02-sessions/hosts.md) for live closure. **Outcome** is a long, readable conversation that stays in place during activity, preserves input through navigation, and can account for exactly one native acceptance at the intended lead. ## Implement the transcript and composer

Own `web/src/features/review/{AgentPanel,Composer}.tsx`, `transcript/{Transcript.tsx,useHistory.ts,history-window.ts}` within that review feature, its navigator, native-question controls and `web/src/api/history.ts`. Extend the M1 files in place. The selected review drawer passes one verified lead and optional child. `AgentPanel` resolves which history to read. It can pass only a verified lead as a send target. The visible child has Conversation and Result, a link to its lead and no message composer. Allow a supported native question from a child to be answered only under its exact question identity. Findings reuses Composer with an immutable report reference and routes feedback to its lead.

| Operation | Read or write behavior |
| --- | --- |
| Read a session | Under `/api/v1/runs/{runId}/sessions/{sessionKey}/history/`, use `page` with opaque continuation or verified `aroundId`, `content` for exact ranges, `navigation` for prompt markers, `plan` for reported steps and `stream` only while this transcript is visible. Each response applies to its captured run, native identity, source generation and query. |
| Send | `POST /api/v1/runs/{runId}/sessions/{sessionKey}/messages` captures the target and a unique submission ID before starting I/O. The receipt carries the same identifiers and the durable state. Show Queued, Delivering, Delivered, Rejected or Delivery uncertain from the returned evidence. A `started` receipt establishes native input acceptance. Resolve a lost HTTP reply with `GET …/messages/{submissionId}`. Reuse the submission ID for an authorized retry. |
| Answer | Read `…/questions` and use `POST …/questions/{requestId}/answer` with the original provider request, turn/item IDs, accepted answer shape and stable submission ID. Native approval or unsupported elicitation opens the named session in the terminal. An ordinary chat message cannot satisfy the form. |
| Intervene | Use the exact selected session’s terminal command/open action and supported interrupt, with visible result. A repeated interrupt or late response cannot clear a newer working state. The last confirmed state remains alongside the observed time when a provider read fails. |

## Prove it

From the same-IID fixture, type distinct text in each lead. Return to A, select an older multiline passage, reveal a tool group, prepend history and receive updates. Verify entry ID, range text, focus and offset survive. Jump by native user landmark. Render a mixed tool/prose turn, an oversized output and an idle missing source. Record mounted rows, charged bytes and open streams. After closing, the previous source has zero active readers owned by the browser. Repeat navigation after a failed read and a newer report notification. Then send one marked A message, immediately view B and disconnect across the acknowledgement. The real provider record and receipt must show one A delivery, zero B deliveries and B’s untouched draft. Repeat a supported exact-question answer and an unsupported native-terminal handoff. Before PACK, exercise the real HOST, HISTORY and REPORT handlers with portable inputs and compare the exact selected native entry, bound receipt/quote and linked session. Run `make web-check`, `make web-build`, `make web-test` and [qualification](../06-release/browser-qualification.md) on the integrated build. Commit a targeted regression only if the established scenario misses a reproduced failure, within the 500-case repository limit.
