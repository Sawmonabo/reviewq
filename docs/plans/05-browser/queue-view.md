# QUEUEUI · Discover work, follow runs and act on notifications

**Start after SHELL and FOLLOW.** Use the confirmed route and selected run with the [worked and busy fixtures](../01-foundation/fixtures.md). Live qualification consumes [source discovery](../03-workspace/sources.md), the [queue projection](../03-workspace/queue.md), native launch/registration and follow-up operations. **Outcome** is a reviewer who can discover an MR, launch selected reviews, find past work and acknowledge precisely the inbox updates they saw. [Queue and settings contract](../../specs/queue-and-settings.md) · [Browser experience](../../specs/browser-experience.md)

## Surface ownership

Own `web/src/app/views/{QueueView,RunsView,AttentionView}.tsx`, `features/queue/{queue-rows.ts,BulkLaunch.tsx}`, `features/Archive.tsx`, `features/Notifications.tsx` and their local styles/operation modules under `api/`. SHELL owns the app registry and the opener/focus return. The view composes the sibling features directly. Use the same launch component for one MR and a selection. The view can supply an explicitly targeted bulk-monitor form using the review feature’s fields via composition. Keep each selection type local to its purpose.

| View | Typed input and output |
| --- | --- |
| QueueView | `GET /api/v1/queue` returns a versioned summary page, facets, full result counts and sync state. Discriminate `mr` and `unmatched_ticket` rows. Send filters/cursor back to the service. Open by MR ID or Jira ticket key. Refresh and Track by URL use explicit commands. |
| RunsView + Archive | Use `GET /api/v1/runs` with the selected stage, query and cursor for mutually exclusive per-MR stage, reason, counts and lead summaries. Use `GET /api/v1/archive` for the archive projection and cursors. Open with the chosen MR and run. Keep unknown membership and missing review dates visible. |
| AttentionView + Notifications | Group each returned event page from `GET /api/v1/notifications` by MR identity. Use the service’s unread MR count for the rail and event count for the inbox. `POST /api/v1/notifications/state` sends the action and frozen event IDs. Read/dismiss is independent of workflow and reviewed-SHA checkpoints. |

## Implement

- [ ] Design each row as a scan from identity to reason to people. Use the ticket key and MR IID/project, title, one reason badge, provider, separate personal approval/our comments/new replies, and labeled author or assignee. Preserve full titles and names accessibly when space is tight. Click/Enter opens its Overview. A ticket-only row says **No matching MR**, shows the Jira assignee and opens Tickets. No launch checkbox belongs on it.
- [ ] Implement Board, Sprint and Repo as a scope, then Ownership, Author, State, Hide, Sort, Clear filters and text search. Keep the result count tied to the same query and settings revision as the visible rows. Hide reviewed and Hide being reviewed independently expose matching counts. Defaults use Active sprints for Scrum and Any sprint for Kanban-only boards. Never combine scope fragments across boards. Drop stale suggestions/responses when selecting another board. Focus search after clearing filters. Distinguish setup/disconnected, initial loading, last successful sync, no scoped reviews and no matches for an active filter.
- [ ] Add **New review → Review MR, Select MRs, Register run** to queue and runs. The picker can track a single explicitly entered MR URL and refresh the choices before preparation. Show native registration guidance first and advanced exact ID entry on demand. Prepare requires the actual configured checkout and open MR. Show exact targets/current revisions, shared provider, skill or custom prompt, arguments, context, compatible model/effort and a preview. Keep the draft when returning from Settings. Use each repository’s real catalog and substitute `{ticket}` independently per target. A dashboard-selected MR associates with the actual native session even when its cwd differs from the MR checkout.
- [ ] In selection mode whole open MR rows toggle checkboxes. **Select all shown** freezes the currently visible, eligible IDs. Reapply the current scope on filter change, dropping hidden or now-ineligible selections before computing count or enabling an action. Keep ticket-only, archived and unloaded rows out. **Prepare reviews**, **Auto-review updates**, **Pause auto-review** and **Cancel** use this exact set. Show the named targets before submission. Batch launch submits one previewed target at a time, records per-MR request/receipt, retains failed/uncertain outcomes and never silently retries or duplicates a launch after a partial response. If launch acknowledgement is lost before a run exists, query `GET /api/v1/reviews/{reviewId}/launches/{submissionId}`. Display the exact saved outcome, known native/run IDs or unresolved status. Keep the same submission ID and withhold a fresh Start until reconciliation. Monitoring edits list available leads/threads separately per MR and preserve mixed outcomes. [Native launch behavior](../../specs/agent-sessions.md) · [Review workflow](../../specs/review-workflow.md)
- [ ] In Runs use four accessible count controls and exactly one stage selection. Awaiting input opens first. Active work, author wait, publish/approval state, archive and unhandled questions follow the returned reason. One card can contain several runs. A different run selection changes transcript/findings and leaves MR-specific code, approvals and tickets intact. Missing source details remain named and reachable for retained runs. In Archived, intersect search, inclusive local date range and a union of board-qualified sprint IDs. Include a historical review date even if a more recent run falls outside range. Show latest matching reviewed date, full stage count and filtered total. Support missing/no sprint/partial metadata explicitly and retain filters when returning.
- [ ] Keep the inbox grouped with latest update, status and full accessible time. Expand to see events with origins and per-item read/unread/dismiss. **Unread** and bounded **All** support pagination. Mark displayed unread events as read in one step, or use the master, group and event checkboxes for selected actions. Capture displayed IDs on selection and preserve them across a concurrent new reply. A newly loaded page or reply stays unselected. On a failed atomic state assignment, keep the captured IDs selected and report the failure. For multiple bounded submissions retain the confirmed chunks and offer retry only for the outstanding IDs. Dismissing an event does not change the MR’s next-action reason. Clicking a matching lead alert opens its target.

## Prove the result

Use two `!41` projects, historical and current runs, a Jira-only row, a blank archive date, same-named sprints from two boards and a new reply that arrives while checkboxes are selected. Inspect one desktop and phone queue, a narrow split with long names, filtered-empty and partial failure. Demonstrate which exact IDs the bulk launch/notification commands used. Compare queue/run totals against the service envelopes before/after scope and stage changes. Exercise search, keyboard and focus return when a row disappears. Reuse the first-slice browser run, extend it only for a demonstrated coverage gap, and run `make web-check`, `make web-build`, `make web-test`. Drive the real queue/runs/notifications/launch/monitor service handlers against the seeded sources after FOLLOW and before PACK. Confirm the renderer reads the same cursors, counts, event IDs and launch receipts as the direct client. Hand those receipts to BROWSERQA for integrated browser qualification.
