# ReviewQ implementation roadmap

**First milestone.** Link a running Codex terminal to an MR, find that run from a second ordinary chat over MCP, open its Changes and Agent tabs, and send one message back to the original terminal. An independent reviewer verifies its native input ID, the selected patch bytes, and the restored file/line after switching reviews. This exercises the Rust service, SQLite, real host, native reader and React entry together before the rest of the dashboard is built. [First review](01-foundation/first-review.md) · [Acceptance](../specs/acceptance.md)

**Starting point.** The greenfield repository at scaffold revision `b2a6da7` contains seven Rust workspace packages, a version-only CLI, and a React shell. The briefs specify future implementation. When implementation starts, record the design revision shared by the workers. For one assignment read the linked brief, its specifications, the applicable repository rules and the accepted predecessor handoffs. ### Scheduling

Earliest acceptance layers, assuming equal task lengths. A slow sibling in an earlier layer holds only its own dependents.

```text
1  CONTRACT · FIXTURE
2  STORE
3  SLICE
4  HOST · HISTORY · SOURCES · SHELL
5  QUEUE · PREFS · ACTION · REPORT
6  FOLLOW · CHATUI
7  ENTRY · TRANSFER · QUEUEUI · REVIEWUI
8  PREFUI
9  PACK
10 BROWSERQA
11 RELEASE
```

- At the start of implementation, dispatch CONTRACT and FIXTURE to separate Sol workers. Start STORE when CONTRACT is accepted, even if generation of the largest fixture is still in progress. At SLICE, check that the production adapters decode the independently generated source inputs. Within SLICE, different workers can own native/provider reads, service/transport operations and browser interactions. The lead gives each an explicit file list from the SLICE brief and reserves one writer for final composition.
- **Qualify the first browser implementation before extending it.** Run SLICE on the representative desktop. Record Chrome’s tab counter at idle, ordinary, large, peak and settled states, backend RSS, time to selectable code, switch latency and frame behavior during a fast scroll with a live update. Confirm the selected line and the native recipient. Use retained reference readings only where the input, counter, interaction and environment are comparable. If a workflow fails or measured cost exceeds the applicable budget, trace and correct the relevant flow or renderer and repeat the affected workload at SLICE. Show the owner the actual everyday tab readings to settle a meaningful memory target. Broader UI work uses the technically accepted implementation. [First milestone](01-foundation/first-review.md#gate-and-independent-review) · [Browser budgets](../specs/acceptance.md#browser-budgets)
- After SLICE meets its technical acceptance criteria, HOST, HISTORY, SOURCES and SHELL can develop together. HISTORY uses the slice's scoped Codex read connection. HOST preserves that read interface while extending management. An extension needed by both goes through a small accepted contract change before the dependent code is wired. QUEUE and PREFS can start as soon as SOURCES lands. They share the accepted scope read model and have different mutation owners. The four browser workers can begin their distinct components after SHELL using its running M1 UI, documented operation examples and the typed integration slots. FIXTURE supplies upstream source inputs. Close each feature only after its production backend predecessors land and its real HTTP/command paths have been registered. CHATUI exercises REPORT and native input, QUEUEUI exercises FOLLOW, REVIEWUI joins FOLLOW with CHATUI to deliver quoted historical findings through the actual composer, and PREFUI exercises ENTRY’s real checkout projection and the preferences operations.
- ACTION and REPORT can run together. Each consumes the accepted native evidence reader and remote source reads. FOLLOW combines their outputs with queue decisions. ENTRY uses FOLLOW for the seventh MCP tool and consumes the other accepted workflow operations. TRANSFER's offline conversion can run in parallel with ENTRY. PACK implements lifecycle and bundle assembly using the accepted dispatcher and production UI. Finalize BROWSERQA from a single staged revision that also contains the accepted offline transfer code, then give that exact bundle to RELEASE.
- With equal task lengths one longest chain is **CONTRACT → STORE → SLICE → HISTORY → REPORT → FOLLOW → ENTRY → PREFUI → PACK → BROWSERQA → RELEASE**. HOST or SOURCES can replace HISTORY, and ACTION can replace REPORT. Actual completion time depends on hosted-session access, the slowest UI or provider lane and the desktop qualification run. Dispatch unrelated ready lanes as soon as their predecessors land.

### Dispatch and merge

1. Use a local integration branch with a recorded accepted commit. Create a separate branch/worktree per task from the commit containing its accepted predecessors. For parallel siblings use the same base SHA, contract revision and fixture version. Record actual worktree paths. Include the accepted design revision and the tracked fixture recipe in each handoff. A code assignment covers its listed paths and tests only. Shared changes go to the named writer.
2. Before parallel implementation, freeze the caller/callee boundary. Give each worker the public types, paths, wire example, route or command identifier, negative case and expected source/output pair. Within SLICE, divide existing prospective files explicitly between native/source, service and browser workers. Reserve CLI/router/module registration, migration number and generated outputs with one writer. If a needed producer has no real caller yet, integrate the smallest runnable producer/consumer pair together.
3. In the task worktree a worker can preview the proposed manifest, registration and generated-output edits as a **local-only wiring patch**. This makes its leaf code compile and run against the pinned contracts. Keep that patch separate from the leaf commit and send both to the integration writer. For a new dependency, resolve on this scratch branch and record the requested package/features and resolved version. Consumers awaiting a changed public shape receive the reviewed producer/consumer interface on one common base before proceeding. Never merge two independently resolved lockfiles or two versions of a generated contract.
4. For each handoff the integration writer starts from the **current** accepted head, applies only the reviewed leaf changes, and reconstructs the shared patch there. Combine dependency requests that first become live in this integration, regenerate both affected lock/type outputs from canonical sources, register all required callers and build the actual app. A sibling on an older base can keep its leaf commits. Recheck its interface, regenerate shared outputs and rerun affected checks at its merge. A changed design contract invalidates the affected handoffs and the lead updates their briefs before redispatch.
5. Record candidate SHA and diff against its base. Run the appropriate locked focused checks, `make crate-deps` after manifest edits, `make web-install` for locked web tooling, `make check` or `make check-low` for cross-stack work, `make web-build` for production assets and `make web-test` against the intended target. The bundle and Playwright each have a separate Make target. Run production reachability checks with the real registration, and supply evidence from the normal CLI, HTTP, MCP, native terminal or populated browser according to the brief. Retain the pre-merge checks as lane evidence.
6. Give the separate Astra reviewer the candidate SHA, predecessor revisions, acceptance inputs and expected observations. They independently exercise the material user path or reconcile its source observations and inspect affected callers. The lead records accepted SHA, reviewer disposition, scoped failures/limits and the next ready IDs. If a fix changes artifact bytes, identify the affected evidence, issue the new hash, and re-run those cases before advancing. Integration of product work is local unless the user separately authorizes publication.

For example, once the accepted SLICE commit has been recorded, a lead can create a local HOST lane from the repository root. Set `accepted_slice_sha` to that recorded commit. Use a fresh branch name for a later attempt and retain the previous worktree and its evidence.

```sh
git rev-parse --verify "${accepted_slice_sha:?record the accepted SLICE revision}^{commit}"
lane_parent=$(mktemp -d)
git worktree add -b impl/host "$lane_parent/host" "$accepted_slice_sha"
git -C "$lane_parent/host" rev-parse HEAD
```

For a requested Cargo addition, apply the manifest delta with its real consumer, run `cargo check -p <package>` once to update the current lock, inspect the diff and run `cargo check --locked -p <package>`. For a direct web dependency, apply the manifest delta and run `pnpm --dir web install --lockfile-only --no-frozen-lockfile` on the candidate, inspect the lock and run `make web-install`. Carry only the integrated locks forward. Rebuild generated browser artifacts from the registered protocol modules. Run the planned `make contracts-check` against the complete schema and output file set. After recording the candidate, repeat `make contracts` and check `git status --porcelain -- contracts web/src/api/generated/` for changed, removed or untracked outputs.

## Completion

Keep synthetic recipes and contract examples in the repository. Keep real conversations, settings, screenshots, traces, per-run logs and private evidence under ignored scratch or a private disposable profile. Use existing checks first. The total first-party automated test ceiling is **500 cases** across Rust and web, counted per parameterized instance. Add a test for a specific uncovered regression and record which existing check misses it. [Acceptance and evidence policy](../specs/acceptance.md#release-evidence)

SLICE acceptance covers its stated Codex workflow. BROWSERQA records measured values and failures for the real artifact, including the open everyday Chrome tab memory target. RELEASE records pass/fail/unverified per installed case and names the supported environments actually exercised. Resolve material failures on the affected revision. Record a missing real host, desktop, profile or user decision as a proof limit and keep the corresponding case open. Stop the task-owned service and preserve the candidate hash, comparison and reviewer receipt for the user. This handoff delivers the implementation plans. Packaging and activation checks use the disposable account specified in RELEASE.
