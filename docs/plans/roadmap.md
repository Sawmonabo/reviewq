# ReviewQ implementation roadmap

**First milestone.** Link a running Codex terminal to an MR, find that run from a second ordinary chat over MCP, open its Changes and Agent tabs, and send one message back to the original terminal. An independent reviewer verifies its native input ID, the selected patch bytes, and the restored file/line after switching reviews. This exercises the Rust service, SQLite, real host, native reader and React entry together before the rest of the dashboard is built. ### Scheduling

These are dependency layers. Several IDs on a line give the lead a choice of ready work. The checkout and writer limits below apply across all layers.

```text
1  CONTRACT · FIXTURE
2  STORE
3  SLICE
4  HOST · SOURCES · SHELL
5  QUEUE · PREFS · HISTORY
6  ACTION · REPORT
7  FOLLOW · CHATUI
8  ENTRY · QUEUEUI · REVIEWUI
9  PREFUI
10 PACK
11 BROWSERQA
12 RELEASE
```

- Begin CONTRACT in the primary checkout. FIXTURE is independently eligible if its generator and expected bytes use external source formats and share no implementation with CONTRACT. Otherwise take it next. STORE follows accepted CONTRACT. Once STORE and FIXTURE pass, keep the first native/source → service → browser path in SLICE with one writer so registrations, readers and client code have one owner.
- **Qualify the first browser implementation before extending it.** Run SLICE on the representative desktop. Record Chrome’s tab counter at idle, ordinary, large, peak and settled states, backend RSS, time to selectable code, switch latency and frame behavior during a fast scroll with a live update. Confirm the selected line and the native recipient. Use the checked-in worked fixture, controlled renderer budgets and the actual headed tab counter. If a workflow fails or measured cost exceeds the applicable budget, trace and correct the relevant flow or renderer and repeat the affected workload at SLICE. Show the owner the actual everyday tab readings to settle a meaningful memory target. Broader UI work uses the technically accepted implementation. [First milestone](01-foundation/first-review.md#gate-and-independent-review) · [Browser budgets](../specs/acceptance.md#browser-budgets)
- After SLICE, choose among HOST, SOURCES and SHELL. HOST extends the existing Codex connection and hands its read-only methods to HISTORY. QUEUE needs SOURCES. PREFS also needs HOST for the native catalog and launch-preparation check. ACTION and REPORT need the accepted native reader, host and provider reads. FOLLOW joins both workflows with QUEUE.
- CHATUI uses SHELL and REPORT. QUEUEUI uses SHELL and FOLLOW. REVIEWUI joins FOLLOW with the real CHATUI composer. ENTRY uses PREFS and FOLLOW. PREFUI exercises ENTRY’s real checkout projection. PACK needs the three completed UI branches of the graph. Stage BROWSERQA with PACK, then give RELEASE that exact bundle.
- With equal task lengths one longest dependency chain is **CONTRACT → STORE → SLICE → HOST → HISTORY → REPORT → FOLLOW → ENTRY → PREFUI → PACK → BROWSERQA → RELEASE**. ACTION can replace REPORT. Actual scheduling also depends on native-host and desktop availability.

### Dispatch and merge

1. **Default to one writer in the primary checkout.** Record accepted local `main`, the design and fixture revisions, affected callers, owned paths and one observable end-to-end result. Use a short-lived local branch in this checkout for the candidate. Include the smallest real caller and its implementation. Review and merge each runnable slice as soon as it passes, before accumulating another slice or waiting for a whole layer.
2. **Add a second writer only for independent work.** The lead records both scopes, accepted prerequisites, each first caller and why the changes can run and be accepted separately. Implement a shared capability, changing contract, registration, schema, lockfile or generator once with one writer and merge it before assigning its consumers. Different filenames alone do not establish independence. Use at most two ReviewQ implementation checkouts in total, the primary and **one** temporary worktree for that second writer. A paused worktree still occupies the slot. Count the integration writer among the two authors. The independent reviewer uses the existing candidate checkout with a private profile. Worktree-provisioning tests use disposable synthetic Git repositories.
3. **Compare behavior before dispatch and again before every merge.** Trace the planned behavior, its callers and existing implementations on accepted `main`. In each active checkout inspect `git diff main...HEAD`, staged changes with `git diff --cached`, unstaged changes with `git diff` and new files listed by `git status --short --untracked-files=all`. Read the new source files as well. Compare both changes side by side for repeated queries, adapters, validation, state transitions or UI behavior even in unrelated paths. Record the matching owners and call sites. When the work overlaps, pause the affected writer, give the common implementation and its first consumer one owner, then redirect the remaining callers to the accepted revision.
4. The integration writer brings the latest accepted `main` into the candidate, registers the actual callers and regenerates affected locks and wire outputs from canonical sources. Record the candidate SHA, diff and focused checks. Run `make crate-deps` after manifest edits, `make web-install` for locked web tooling, `make check` or `make check-low` for cross-stack work, `make web-build` for production assets and `make web-test` against the intended target. Exercise the brief's CLI, HTTP, MCP, terminal or populated browser entry. Keep acceptance evidence for that candidate.
5. The separate Astra reviewer independently checks the material user path, source observations and affected callers on the recorded candidate. The lead records the disposition, evidence, proof limits and accepted SHA, and fast-forwards local `main` to the reviewed commit. If `main` advances during review, integrate it and repeat the affected comparison, checks and review. After each merge, bring any remaining lane onto the new accepted base, update ownership and retire duplicate proposals before resuming. Close a brief only after its full acceptance. Publication requires separate user authorization.

For a requested Cargo addition, apply the manifest delta with its real consumer, run `cargo check -p <package>` once to update the current lock, inspect the diff and run `cargo check --locked -p <package>`. For a direct web dependency, apply the manifest delta and run `pnpm --dir web install --lockfile-only --no-frozen-lockfile` on the candidate, inspect the lock and run `make web-install`. Carry only the integrated locks forward. Rebuild generated browser artifacts from the registered protocol modules. Run the planned `make contracts-check` against the complete schema and output file set. After recording the candidate, repeat `make contracts` and check `git status --porcelain -- contracts web/src/api/generated/` for changed, removed or untracked outputs.

### Cleanup after each merge

The lead keeps a private ledger of task-created branch names, checkout paths, temporary roots (including their parents created for the task), processes and output destinations. Record scratch and retained evidence separately at creation. This includes build/dependency directories, generated fixture repositories and worktrees, databases and sidecars, disposable native/browser profiles, logs, traces, screenshots, packages and QA output under or outside the checkout. Direct new output into task-owned locations. Record any existing shared cache or pre-existing files to preserve.

1. Stop the task’s services, hosts, browsers and fixture servers. Save the accepted SHA, artifact digest, measurements and reviewer receipt, plus any required private artifacts, outside the directories to be removed. Inventory `git worktree list --porcelain`, branch tips and each checkout's `git status --short --untracked-files=all`. List ignored paths by directory with `git ls-files --others --ignored --exclude-standard --directory`. Inspect them locally against the ledger, including any unexpected contents inside generated directories and external roots. An unexpected file keeps its checkout or directory in place until ownership is resolved.
2. Use the primary checkout on the receiving branch. Set `accepted_ref` to local `main` or the recorded temporary integration branch that accepted the slice. Verify its accepted SHA, re-read the task branch tip and require it to match the ledger. Run `git merge-base --is-ancestor "$tip" "$accepted_ref"` and require exit 0. Keep the integration branch until its own tip passes the same check against `main`. For a squash, cherry-pick, diverged tip or uncommitted work, keep the branch and any unique files, report what remains and reconcile outstanding work with its owner. Matching patch bytes alone do not establish Git ancestry.
3. Delete only the verified, ledger-owned generated files and disposable directories, including ignored artifacts. Preserve versioned deliverables, unrelated user files, shared caches and retained private evidence. Once the temporary checkout is clean, run `git worktree remove "$worktree"` from the primary checkout, then `git branch -d "$branch"` after the ancestry check. For work done in the primary checkout, switch to the accepted receiving branch before deleting the merged task branch. Apply the same reachability and deletion steps to any temporary integration branch at final acceptance. A refusal leaves the work available for inspection. Avoid force removal, `git clean -fdx` and global cache pruning.
4. Remove the recorded, now-empty temporary parents with `rmdir`. Read back the worktree list, local branches, checkout status and every owned output path. Record each removal or retained evidence path. Keep unresolved items open with a named owner.

## Completion

Keep synthetic recipes, contract examples and qualification procedures in the repository. Record per-run measurements and outcomes with the candidate. Keep sensitive recordings and logs private. Each fresh run regenerates its inputs from tracked sources. Use existing checks first. The total first-party automated test ceiling is **500 cases** across the entire repository, counted per parameterized instance. Add a test for a specific uncovered regression and record which existing check misses it. [Acceptance and evidence policy](../specs/acceptance.md#release-evidence)

SLICE acceptance covers its stated Codex workflow. BROWSERQA records measured values and failures for the real artifact, including the open everyday Chrome tab memory target. RELEASE records pass/fail/unverified per installed case and names the supported environments actually exercised. Resolve material failures on the affected revision. Record a missing real host, desktop, profile or user decision as a proof limit and keep the corresponding case open. Stop the task-owned service and preserve the candidate hash, comparison and reviewer receipt for the user. Packaging and activation checks use the disposable account specified in RELEASE.
