# RELEASE · Qualify the installed product

**Goal.** Prove that the exact distributable runs a complete review in an independent user account, preserves its work through a same-schema update, and works with real native hosts and the production browser. The review result identifies the workflows and operating environments actually exercised. [Operations](../../specs/operations.md) · [Acceptance](../../specs/acceptance.md)

**Needs.** BROWSERQA on the final packaged revision, including accepted PACK and the integrated application. Reuse FIXTURE's deterministic ordinary, quiet and 12k-line scenarios and the SLICE native-session receipts. A result can be reused when the shipped bytes, machine, host, input and procedure still match the claim. The final package goes through the real launcher and host installation. The builder and an independent reviewer perform the release checks from the same revision.

## Produce the candidate

- [ ] Use the integration writer's accepted `Makefile` package target and CLI wiring in `crates/reviewq/src/main.rs`. RELEASE owns their end-to-end qualification and the user installation/troubleshooting instructions in `README.md`. Fix cross-feature wiring in its owning module with the feature worker. Record the candidate's results at a caller-chosen output location and protect sensitive traces. The tracked repository must contain each synthetic input or its complete reproducible generation procedure. Avoid a second automated end-to-end suite that repeats these checks.
- [ ] From a fresh checkout at a named revision run `make web-install`, `make check`, `make web-test`, then `make package`. Browser automation prerequisites and the tested browser version are part of the build record. Record Cargo and pnpm lock digests, host/target triple, runtime loader, package bytes, binary/manifest digests, versions of both agent CLIs, web asset IDs and licensed bundled components. Check the build inputs include every referenced host and web file.
- [ ] Copy only the release directory to a disposable user account or Linux/WSL VM with its own user manager, browser profile, Git checkouts and local native configuration. Start in an unrelated directory. A changed HOME alone does not isolate the systemd user manager, desktop notification identity or signed-in native daemon. Use the FIXTURE projects alpha/11 and beta/22, both at !41, tickets RQ-41 and RQ-42, distinct native owners and unique safe sentinels. Add a second open MR for one ticket when exercising ambiguous registration. Use private disposable GitLab/Jira targets or the documented FIXTURE read endpoints. Record exactly which provider operations were real, replayed or unavailable.
- [ ] Install in a second empty disposable account and open first-run setup. Apply a same-schema candidate over the populated installation, reopen the current store and check its prior registrations, decisions, report versions and pending receipts. In a separate profile point installation at an unrecognized file and verify its bytes and the managed paths are untouched.

## Start a new review from an ordinary management chat

Exercise RUN-2 independently of terminal linking and dashboard launch. In the disposable provider input, add two open, eligible MRs with the same IID (91) in the configured alpha and beta projects. Supply real checkouts for each. Start an ordinary Codex chat in the first configured checkout and an ordinary Claude chat in the other. Neither management chat is linked. From each native MCP client, call `search_reviews({"filter":"unstarted"})` and `get_review({"target":"<its exact MR URL>"})`. Follow list pagination and confirm both targets have **zero runs**. Keep their original scoped IDs, checkout paths and observed head SHAs. This exercise creates the first lead for each target, without first visiting the review in the browser or linking a conversation.

1. In the ordinary Codex chat explicitly request a **Claude** review of alpha!91. In the ordinary Claude chat explicitly request a **Codex** review of beta!91. Use the native clients' installed `start_review` tool. The following are complete argument examples for synthetic heads. Substitute the actual URL and verified full SHA from each preceding read. Record one new UUID per independent launch. The example's custom prompts allow the host defaults for model/effort.

[

Record QA-ALPHA-91."},"context":"Private review. Leave GitLab unchanged."},
  {"target":"https://gitlab.example.test/forge/beta/-/merge_requests/91","provider":"codex","submissionId":"04dedf4c-e47d-4508-83f6-e92f27cb0091","expectedSha":"bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb","invocation":{"mode":"custom","prompt":"Review the lexer in this MR only. 2. Send each object as one separate MCP call. Keep the actual emitted tool result for each submission, including its reported state, scoped target, run and any native session identity and dashboard URL. Where the initial result is pending or uncertain, inspect the saved launch to its observed outcome. Read back with `get_review`, follow the returned link in the installed browser, and open that exact native lead. Compare provider, cwd, requested SHA, actual turn/prompt and marker to the original request. Require one native lead for alpha and one for beta, distinct from both callers, one occurrence of the corresponding launch prompt per lead and none of the other's marker. Both management chats remain ordinary. Let each lead finish its first review turn without a second prompt. Open Findings on each run and compare its accepted receipt, hash and reviewed SHA with the lead’s actual handoff. A pending receipt or a report assigned to the other lead leaves that case open.
3. Repeat the first call with its unchanged arguments and UUID. For the second, drop the response after native acceptance on the disposable transport, reconnect and inspect the existing attempt, then resubmit only the identical original call. Confirm the existing receipt/run is recovered and there is exactly one registered run and one native session creation per target. A pending outcome remains pending until receipt/host evidence resolves it. A replay with the same UUID but altered request must fail without creating a session. Supply an unconfigured target from a grantee and try discovery from an unconfigured checkout. Check the scoping failures leave both target counts unchanged. Record unavailable fault-injection or native evidence separately. [MCP tool contract](../02-sessions/entrypoints.md) · [Native launch](../02-sessions/hosts.md)

| Read, refresh and decide locally | Request a refresh via the queue and `reviewq refresh` while the first request is active. Verify the reported completion, scoped rows, counts, sync time and failure state against the generated source data. Open same-IID MRs from each repo, confirm ticket details, commits, files and discussion positions. Exercise queue filters, **Notifications**, **Archive** and local review/ack commands. Preserve the old successful data and show its age on a provider timeout. |
| Native registration and management | Open a new Codex terminal at a configured checkout, show the dashboard unlinked and explicitly link the current conversation. In Claude link a different real session using its own `/reviewq`; verify host version and displayed exact identity. Use both native management clients in an ordinary chat to list scoped reviews and inspect the selected report/transcript. The management session stays unregistered. Check an unconfigured checkout cannot use another checkout's grant. Reopen a new worktree and verify the managed setup reaches that same service. |
| Launch, converse, reopen | Start a new native review from the dashboard with selected skill/arguments/model and then launch a small batch covering both projects. For Codex check the actual shared daemon, exact thread/turn and configured capacity/recovery behavior. |

A tool result alone is insufficient. Send the lead feedback for one finding, record an explicit user disposition, and verify a chat-turn update to one finding preserves the other finding, report ancestry and the requested scope. Inspect an older version and an unfinished review independently. |

Arm a selected-thread check, publish a reply, exclude another discussion and produce a narrow report at a new SHA. | Browser and performance | Run the BROWSERQA matrix at the packaged URL, on the actual desktop/WSL path used by the operator. Record host versions and individual results. |

## Decide and hand off

Record RUN-1/2, SEND-1, HIST-1, DIFF-1/2, FIND-1, WORK-1 and OPS-1 plus each browser budget from the [acceptance matrix](../../specs/acceptance.md). Classify every row and its required subcases as passed, failed or unverified. Record inputs, expected and observed outputs, build and host identity, private evidence location, OS/architecture and limitations. Keep timed outcomes with their timing boundaries and input sizes. Distinguish a withheld remote mutation, unavailable host sign-in, simulated transport, missing real trackpad or fixture-only observation from a verified native result. An unverified required flow remains open for that release target.

An independent reviewer installs the same bundle, reproduces at least one source-to-accepted-report run, checks its native owner/receipt/bytes against independent inputs, reviews the worst observed browser measurement and compares the restored release/data identities after failure. Close only after resolving functional failures and accounting for every acceptance row. Record new digest and rerun affected paths after a fix. Leave task-owned services stopped and remove their managed registrations using their own verified launcher. [Release evidence](../../specs/acceptance.md#release-evidence)
