# PREFS · Save connections, team scope and repository bindings

**Needs** accepted SLICE, STORE and [SOURCES](sources.md). **Delivers** a validated personal workspace to the runtime, launcher, review collector and [Settings UI](../05-browser/preferences-view.md). QUEUE uses the existing immutable settings read port and can progress independently. The installed product supports one GitLab origin/account and one Jira Cloud site per workspace. Open the [workspace specification](../../specs/queue-and-settings.md) before implementing the operator-facing fields. ENTRY owns the native config projection. PACK owns installation and the machine-local non-secret startup file. Codex recovery and FOLLOW's automatic/concurrency policies use their independent private SQLite revisions.

## Files and public surface

| Files | Responsibility |
| --- | --- |
| `crates/domain/src/settings.rs` | Non-secret `BoardScope,RepositoryBinding,VerifiedIdentity,SettingsRevision`, immutable scope relationships and revision comparisons. Default empty configuration. Keep platform path inspection and provider IO outside domain. |
| `crates/app/src/settings.rs` | `get_settings() → SettingsView`, `test_connection(ProbeDraft) → VerifiedConnection`, `lookup(CatalogQuery) → CatalogResult`, `save_settings(ExpectedRevision,SettingsDraft,TokenChanges) → SettingsView`, `disconnect(ExpectedRevision,Provider) → SettingsView`. Consume shared source reader factory, checkout/native catalog, committed settings repository and private grant/projection ports. |
| `crates/store/src/settings.rs` | Read and conditionally replace settings, credentials, workspace identity, checkout-grant generation and projection intent in STORE's private database. Use transaction-scoped reads and writes. Keep ordinary settings serialization completely separate from the private credential read method. |
| `crates/protocol/src/settings.rs`, `crates/transport/src/settings.rs` | Implement strict allowlisted wire DTOs and the versioned Settings and Codex recovery preference operations. Apply CONTRACT's local mutation guards to draft test/catalog as well as save/disconnect. Return sanitized typed field/connection errors and current revision when a write conflicts. |
| `crates/reviewq/src/main.rs` | The integration writer registers PREFS's wiring for the one active revision to QUEUE, source factory, launch preparation and ENTRY's private file projection. Share the provider limiter with background tasks. Call the same activation/reload code on restart. |

The table uses abbreviated wire types. Stable identifiers and revisions are strings, label/URL/path fields are display metadata, and optional fields accept explicit null as shown. Keep unrecognized fields and invalid provider/kind combinations out of the adapter.

| DTO or operation | Fields, behavior and bounds |
| --- | --- |
| `SettingsView` | `{settingsRevision,mode,connections:{gitlab,jira},boards,repositories,additionalReviewerIds,chatSetup}`. Modes `setup,connected,disconnected`. GitLab summary `{origin,configured,identity}`, Jira summary `{site,email,tokenType,configured,identity}`. Identity is null until verified, else `{id,label}`. Unconfigured connection fields may be null. Return `chatSetup:{state,issues}` with `state=ready,pending,cleanup_conflict`. Issues are safe path-scoped summaries. Save waits for validation and local commit. Projection issues are visible separately. |
| `SettingsDraft` | `{gitlab:{origin},jira:{site,email,tokenType},boards,repositories,additionalReviewerIds}`. Origins are HTTPS with no path, query, fragment, embedded userinfo or untrusted redirect. `tokenType=scoped,unscoped`. Verify Jira site/cloud/account and GitLab origin/user under credentials. No installation-specific default origin, projects, boards or skills. |
| `BoardScope` | `{scopeId,boardId,name,type,enabled,projectIds,reviewStatusIds,jiraProjectKeys,teamFilterId,storyPointsField}`. Resolve name and Scrum/Kanban type from the verified provider. For enabled boards require at least one known status ID and selected project after applying Any tracked board. Optional saved team filter ID is numeric. Project keys and optional `customfield_<digits>` must validate before inclusion in structured Jira reads. Reject duplicate board IDs, scope IDs, duplicate repository IDs or references to missing repositories. Accept zero enabled boards as a deliberate paused discovery scope. |
| `RepositoryBinding` | `{projectId,path,checkout,boardSelection,defaultSkills}`. Canonical GitLab namespace comes from project read. `boardSelection=selected,any` chooses either explicit board associations or every **configured** board including future additions. `checkout=null` permits discovery/tracking. Existing absolute local Git directory required for launch. Canonicalize top-level and common dir. `defaultSkills` maps supported provider to an exact provider-advertised skill name/path. Verify selected skills in the chosen checkout and revalidate at launch. Paths may contain spaces and linked worktrees. |
| PUT /settings | `{expectedRevision,draft,tokens:{gitlab,jira}}`. Each token operation is `{action:"keep"}` or `{action:"replace",value:<nonempty private input>}`. Up to 8,192 characters per replacement. Blank browser input becomes keep for a bound saved connection. Disconnect is a separate explicit command. Ignore display labels supplied by client after verifying IDs. Return the new view only after commit. |
| POST /settings/test | `{expectedRevision,provider,connection,token}`. Verify exactly the selected identity and its draft. On GitLab, GET current user and read a member-project page. On Jira verify site/cloud binding and GET myself. Return `{provider,identity:{id,label}}`. An empty accessible project page is valid. This is a remote read. The result neither saves a secret nor activates a new settings revision. |
| POST /settings/catalog | `{expectedRevision,provider,connection,token,kind,q?,cursor?,boardId?,view?,states?}`. GitLab projects supports member/starred/all, Jira supports boards, board metadata, statuses, saved filters and board sprints. `q` up to 200 characters, provider page ≤100. A successful list returns `{items:[{id,label,path?,boardId?,state?}],nextCursor}`. For one board's metadata include normalized board type, known status IDs and estimate field. Continuations bind provider/host, credential generation or draft, kind, board, view, query and revision. Invalidate stale result on any change. Use `POST /runs/catalog` from HOST for local provider model/skill discovery. |
| POST /settings/disconnect | `{expectedRevision,provider}` deletes the named stored provider credential, invalidates its clients and pauses remote collection. Keep the remaining connection, verified history, choices, grants/agent sessions as authorized by their own checkout policy. Require explicit confirmation in Settings. Return the new disconnected view. |
| Agents controls | Global automatic follow-ups default off. Maximum simultaneous follow-ups defaults to 2, valid 1–8. Read/write the dedicated `/api/v1/followups/preferences` resource and its revision independent of provider connection settings. Automatically resume interrupted Codex reviews defaults off. PREFS owns `GET/PUT /api/v1/settings/agents/recovery`, returning `{revision,autoResumeCodexReviews}` and accepting `{expectedRevision,autoResumeCodexReviews}`. Use an independent SQLite preference revision. HOST supplies cancellation/wakeup after the committed change and a separate per-lead explicit cancel. Incoming completed host work remains readable after toggles. Specific holds/cancellations, current-vs-new native turns and per-MR overrides belong to HOST/FOLLOW. |

An empty view and one accepted update example follow. These are response `data` and request fragments. The local API supplies the success/error envelope.

```json
{"settingsRevision":"0","mode":"setup","connections":{"gitlab":{"origin":null,"configured":false,"identity":null},"jira":{"site":null,"email":null,"tokenType":null,"configured":false,"identity":null}},"boards":[],"repositories":[],"additionalReviewerIds":[],"chatSetup":{"state":"ready","issues":[]}}
```

```json
{"expectedRevision":"7","provider":"gitlab"}
```

If revision 7 held two configured connections, an accepted disconnect returns revision 8, mode disconnected, GitLab configured false, Jira configured true. A later request with revision 7 reports a conflict and leaves revision 8 intact. The UI cannot derive a verified connection from the presence of a typed token.

## Implement and qualify

- [ ] Create private storage in STORE's existing owner-only profile. Reuse `settings`, `credentials` and `repo_grants` instead of introducing a second settings database. Maintain verified originating GitLab user ID and Jira site/cloud/account identity across disconnect. Protect parent 0700, database, journal/WAL/SHM and credential material 0600 under a private process umask (OS-account protection). Route stored token lookup through a private adapter. Domain and ordinary response/log DTOs must have no access to raw credentials. Never print drafts or serialize secrets in error/debug output, cache keys, query strings, command arguments or event bodies.
- [ ] Bind credential reuse to saved origin and auth identity **before** network access. A changed GitLab host or Jira site/email/token type requires replacement. For a workspace with history, reject a different site/origin before transmitting any saved secret, verify the original account after reading identity and reject an account change. Disconnected or expired credentials must not trigger fallback to another CLI, profile or environment file. Keep ephemeral probe and catalog clients separate from active source context. Reuse their network budget. Cache only successful saved-credential catalogs, keyed by settings revision and stable request identity, 5-minute TTL and 8 MiB combined LRU. Never cache replacement tokens or share draft pages across connections.
- [ ] Validate the whole candidate before activation. Use GitLab to resolve each project ID/current namespace and Jira to verify board metadata, each enabled board's statuses, project restriction/team filter and a scoped read. A read-denied board, ambiguous simple-board sprint feature or invalid estimate field is an English field-specific error. Resolve relative or missing checkout explicitly, verify Git top-level/common dir outside the database, and enumerate actual per-provider skills for the selected checkout. Reject a default that has disappeared or cannot be disambiguated. A repository with no checkout is a valid source. Never change a business checkout just to validate it.
- [ ] Commit on `expectedRevision` inside a short transaction. Mutually serialize final settings activation, pending native launch acceptance, decision CAS and source publication, checking the active revision at each effect boundary. Store whole validated configuration, credentials, verified account bindings, grant changes and scoped invalidation atomically. A failed validation/commit leaves the previous version effective. On success discard stale cache entries, publish the effective version and schedule coalesced background refresh. Prepared launches must revalidate project, SHA, actual checkout, default skill and revision. Do not restart an already linked host conversation. Boot reloads the committed version even if activation notification was interrupted.
- [ ] Let a strictly access-reducing update (removing a checkout/repo and associated board links/defaults, same connections) revoke access offline. Distinguish this narrow operation from an addition, path change or secret replacement. For each binding create/reuse a grant only for its verified installation, origin/project, canonical root/common-dir and current grant epoch. The store keeps its token verifier and, where needed for installation, private managed credential material with the same protection as other secrets. Grant identity authenticates an allowed checkout. Its authorized management targets can span all currently configured projects per ENTRY. Revoke a removed/rebound issuing grant for every target in the settings transaction immediately. Removing a target project excludes it for every remaining client. Persist desired/applied projection revisions and safe cleanup state. Persist a pending receipt that is independently usable before native projection ships. Then, when ENTRY is installed, call `RepositoryChatProjection::reconcile(settings_revision)` **outside** the transaction. On restart resume a pending projection of the current generation. A failed cleanup cannot reauthorize an old token. Show named pending/conflict state until reconciled. [ENTRY](../02-sessions/entrypoints.md)
- [ ] Provide safe form semantics through [PREFUI](../05-browser/preferences-view.md). A typed search or test acts only on its provider draft, with abort/epoch guard for a superseded response. Add board/repo focuses the actual new editor. Selected boards and Any tracked board edit the same scope used by discovery. Direct Save validates and activates. Keep dirty non-secret edits on a conflict for explicit reconciliation. Wipe transient secret controls on success, cancel, close or a confirmed disconnect. Never render a stored token. Independently saving an Agents preference must not submit/revalidate an unsaved connection/board draft. Test/catalog authority ends with that operation.

Run `cargo check --locked -p reviewq-store`, `make crate-deps` and `make rust-check`. For this backend handoff use the real save, scoped grant authorization and pending projection receipt. A synthetic projection adapter can acknowledge, delay or return a cleanup conflict. ENTRY owns the later real native config, restart and MCP readback. PREFUI owns the real Settings controls. Use a synthetic workspace, synthetic credentials and the normal routes. A real user credential is unnecessary for regression proof.
