# Desktop notifications and browser alert preferences

**Implementation plan.** A reviewer should recognize the ticket, the MR and the event in a glance. Clicking a browser-delivered alert should bring the reviewer to its exact inbox entry in an existing tab. Browser permission has one home under **Settings → Preferences → Notifications**. The installed behavior is described in [Operations](../../specs/operations.md).

## What a reviewer sees

Use two text fields. The title is `<ticket> · MR !<iid> · <event>`. Use the first linked ticket in the inbox’s stable order when several apply. The inbox retains its current bounded list of linked tickets. With no ticket, use a recognizable repository name, e.g. **platform-web · MR !42 · Findings ready**. If two scoped projects would have the same displayed identity, include the distinguishing project path and, for identical paths on different instances, the GitLab host. Navigation always uses the opaque occurrence ID. Keep the MR number and event readable when shortening a long project name.

| Example title | Example second line |
| --- | --- |
| RQ-41 · MR !42 · 3 new replies | Across 3 review discussions. |
| RQ-41 · MR !42 · Codex needs your answer | Which revision should I review? |
| RQ-41 · MR !42 · Findings ready | 2 findings · 1 blocking |
| RQ-41 · MR !42 · Report update failed | Your last accepted findings are still available. |
| RQ-41 · MR !42 · Follow-up complete | 2 discussions checked · findings unchanged. |

These examples use synthetic data. Include a single short, verified detail. Format singular and plural, including zero, explicitly. Normalize whitespace, strip control characters, use plain text and use the existing Rust grapheme support to shorten text. Budget the encoded title and body together within the desktop protocol frame limit, including JSON escaping. Use a short native question only when a display-safe prompt is available. Otherwise use “Open Agent to answer.” Keep tool arguments, code, links with credentials, transcript bodies and raw provider errors out of desktop previews. Omit an unsupported detail. Windows and Chrome supply application identity in their own UI. [Windows notification guidance](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-ux-guidance)

| Event evidence | Title suffix and useful detail |
| --- | --- |
| GitLab reply, edit, resolved or reopened discussion | “New reply”, “Reply edited”, “Discussion resolved” or “Discussion reopened”. For a batch, count distinct replies and discussions from the event members. Mixed changes can say “3 discussion updates” / “2 replies · 1 reopened”. |
| Reviewed head changes or personal approval is withdrawn | “New commits after review” or “Your approval was withdrawn”. Use a verified short head or the project for context. |
| Native question, permission, failed turn or Codex usage limit | Name the provider and the event, e.g. “Claude needs permission” or “Codex turn failed”. Give one useful next action. For a known account-wide quota episode shared across reviews, use “Codex usage limit” as the title and the affected review context in the body. |
| Published version, unfinished or refused review, or `needs_input` | “Findings ready”, “Report update failed” or “Review needs input”. Use the count and blocking dispositions from that published version. Distinguish an unfinished full review from an unfinished selected-thread check (“Follow-up update failed”). Mention earlier findings only if a published version exists. An update that keeps its parent's attention lineage stays silent. |
| Accepted scoped follow-up or unconfirmed publication | “Follow-up complete” with the proved result, or “Publication needs verification” with the affected comment or approval when known. A successful scoped final that changes findings uses its verified findings result. |

## One owner for presentation and delivery

1. Keep event detection with GitLab, the two native providers, reports and actions. Keep the existing transaction-local [deduplicating insert](../../../crates/reviewq-store/src/notifications.rs), unread state and delivery receipts. Retries of one occurrence retain its identity. Two distinct submissions retain two inbox records even when both failed on the same run.
2. Extend [the existing Rust notification module](../../../crates/reviewq-app/src/notifications/desktop.rs). Give it typed event facts and a bounded set of eligible members. Return the title, optional detail, representative notification ID and replacement key. Use the same event vocabulary for the inbox label and toast. Remove duplicate failure strings from both report paths and reconcile the React inbox label map. Preserve readable existing rows whose structured evidence is missing. Audit the unused `followup_needs_input` spelling across stored rows, the wire contract and UI before retiring code. A reserved spelling alone never creates a new toast.
3. The [store](../../../crates/reviewq-store/src/notifications/desktop.rs) supplies local facts for the claimed members in bounded set queries. Reuse the scoped/retained ticket lookup in the inbox, GitLab discussion evidence, native session provider, review pass kind/base and published revision, and follow-up results. Include source when distinguishing a native question from a `needs_input` call. Prefer existing durable joins. If evidence would otherwise be lost, add only the small fact required at insertion and support absent values in existing profiles. Use a plain, specific failure reason only when the evidence selects it. Several checks yield the same report-base error. The broader error alone cannot establish which check failed. Formatting requires zero provider calls, transcript scans or Markdown parsing. Keep platform I/O outside the write transaction.
4. Group pending routine discussion changes by review using the current 25-member limit. Give each actionable request its own group and replacement key, scoped to the exact session/request or workflow occurrence. Recheck the exact request before display. A confirmed closure or answer suppresses the stale prompt while retaining its inbox history. When current state cannot be proved, use historical wording such as “Codex asked a question” and routine priority. Keep failures and report outcomes separate from discussion traffic. Preserve the single desktop receipt for a known Codex quota episode across MRs. The existing single dispatcher arbitrates eligible fresh claims and due retries together. Start with actionable work. While both classes have eligible work, alternate up to four actionable deliveries with one oldest routine group. Within a class use oldest eligible first. Keep the small scheduling counter in this worker and reset it at startup. A new permission request can wait behind the routine delivery already selected, and routine events still progress under sustained action traffic. Check both directions with an aged backlog, including due retries. Select a representative from the surviving unread members and link to the occurrence described by the headline. Count only members actually in that delivery.
5. Split-claim, permission and restart races use the existing [dispatcher](../../../crates/reviewq/src/runtime/desktop.rs). After the browser accepts an offer, recheck membership and the **whole presentation** before display, including current actionability, destination and replacement key. Cancel a stale offer and send only the current eligible presentation. Keep muted/read/dismissed events in the inbox according to existing rules. A lost display acknowledgement or interrupted claim remains uncertain and ineligible for automatic replay. A provable rejection before display can fall back once. Bound retries using the existing receipt.
6. Rust derives the existing Windows-compatible 16-hex-character hash from an unambiguous encoding of scope and group purpose. Use the account episode in place of the review for shared quota alerts, so the representative MR can change without changing the key. Give Chrome and Windows that exact key. New routine batches for a review may replace an older routine alert. A new reply cannot replace an outstanding question. Scope replacements to each notification channel and preserve all inbox occurrences. Keep the Linux sender’s exact inbox link, escaped body and shared text. Linux notification servers replace by a server-issued numeric ID. Use replacement only where the sender can reliably retain that ID for the running server. [Browser notification tags](https://notifications.spec.whatwg.org/) · [Linux notification protocol](https://specifications.freedesktop.org/notification-spec/latest/protocol.html)

### Connect the reply with what happened next

Join the triggering notification through [follow-up observations and members](../../../crates/reviewq-store/src/schema/followups.sql) to the exact batch and [confirmed native start](../../../crates/reviewq-store/src/hosts/delivery/workflow.rs). Show “Codex started a follow-up” on that activity only after a proved automatic start. A queued, reserved, held, manual or uncertain submission cannot claim it. Read the batch’s member IDs when invalidating the affected inbox projection. Page and exact-item reads must also efficiently traverse notification ID to observation. Check EXPLAIN QUERY PLAN against a populated backlog. If needed add a partial index on followup_observations(notification_id) for non-null IDs through the store’s schema path, verifying both fresh and existing profiles. A pending toast can include this detail. For an already delivered toast, update the inbox item quietly. Its occurrence ID, unread state and desktop receipt survive. Opening or refreshing notifications never starts a review.

## Clicks and Settings

**Clicks.** Negotiate the presentation version in the authenticated browser Hello/Ready exchange before registering a delivery client. An old tab can silently ignore new offer fields and apply its own tag. A mismatched handshake must decline cleanly and permit native fallback. Version the worker-to-tab readiness reply as well, since the cached shell and active worker can update independently.

Extend the [service worker](../../../web/public/notifications-worker.js) and [tab receiver](../../../web/src/features/notifications/browser-alerts.ts). Offer the exact ID to compatible tabs, most recently focused first. Ask the shell whether it can leave the current view without discarding edits. A dirty Settings form, unsaved launch or monitor form, or in-flight save declines the offer. Recheck immediately before routing, since edits can begin after readiness. Preserve saved composer drafts. Visit one eligible tab and acknowledge success after the route commits and the inbox focuses the matching entry. A retained read or dismissed entry is a valid target. An exact missing or inaccessible target gets a terminal unavailable state in the inbox. A slow data fetch can acknowledge that navigation was accepted, then finish in the same tab. A transient fetch failure exposes the existing inline Retry in that tab. Keep navigation acceptance distinct from confirmation that the item opened.

Use one bounded click attempt with correlation IDs, deadlines and a current-route status check. A late or repeated message for the same attempt is idempotent. If the first tab never accepts navigation or disappears, try the next compatible tab. If an accepted tab loses its reply, query its current attempt/route before retrying. Its mere presence cannot acknowledge the click. Fence expired attempts so a late tab cannot steal focus back. A newer click or deliberate manual navigation supersedes the earlier attempt and cancels its focus and new-tab fallback. Use one new tab as the last resort when no compatible tab can handle the link. Native fallback opens the same exact URL through the OS. The user's default browser controls tab reuse in that path.

**Settings only.** Add **Notifications** under the existing **Preferences** heading alongside Appearance. The row reads **Open desktop alerts in this browser**. Its supporting line explains that clicking an alert returns to an open ReviewQ tab when available. Reuse the existing permission subscription. Render the same row in [both Settings paths](../../../web/src/features/settings/SettingsPane.tsx), including when workspace settings cannot load.

| Browser state | Row behavior |
| --- | --- |
| Permission available | **Enable** requests permission from the user's click. Dismissing the prompt keeps Enable available. |
| Granted | Show **Enabled**. A permission change in browser settings updates the row and channel. |
| Denied | Show **Blocked by browser** and **How to allow**, with inline site-permission instructions. |
| Unsupported or development preview | Show an appropriate unavailable explanation. |

This row reflects browser permission immediately and operates independently of workspace Save, appearance choices and the service's `desktopNotifications` mute. If service delivery is muted and that fact is available, identify it separately. Remove the inbox enable button and its header spacing, preserving the connection-warning slot and the inbox selection toolbar. [Browser permission guidance](https://web.dev/articles/permissions-best-practices)

## Implementation sequence

| Slice | Depends on | Owner, change and acceptance |
| --- | --- | --- |
| Settings placement | Existing permission API | Web writer owns Settings, the permission row and its removal from the inbox header. Exercise the populated modal at desktop and phone widths, keyboard return, external permission changes, denied/default/granted states and unsaved workspace edits. |
| Message and grouping | Existing inbox and worker | Rust writer owns the app formatter, store queries/claim selection, producers and inbox wire projection. Use one synthetic fixture with two projects sharing an IID, multiple tickets, three replies on distinct threads, an outstanding question and two genuinely different failed handoffs. Verify context, fallback, counts, priority, destination, re-reading after restart and one occurrence per source event. |
| Platform delivery | Message and grouping | Extend the existing browser offer and native senders. Share the title/body/key/destination across adapters. Exercise mixed-version tabs, an explicit rejection, loss after display, state changes during an offer, and consecutive routine alerts around a pending question. Confirm exact Windows/Chrome tags and OS acceptance in an isolated desktop fixture. |
| Follow-up status | Message and grouping | Connect the existing confirmed-delivery write to the originating inbox activity. Compare held, manually started and confirmed automatic outcomes on the same fixture. Verify the activity updates once and the desktop delivery count stays constant. |
| Click recovery | Settings placement and browser offer settled | Web writer owns worker, tab receiver and route/focus acknowledgement. Replay two compatible tabs, a lost reply, a disappearing tab, a slow exact-item read, a dirty draft, a dirty Settings form as the only tab and alongside an eligible second tab, a cached old tab with a new worker, successive clicks A then B while A is loading, and zero open tabs. Check the final focused occurrence, draft, and number of new tabs. |
| Integrated acceptance | All slices | Review the merged production bundle against the same fixture, verify that re-enabling delivery after a mute or restarting with an unanswered prompt cannot replay a delivered toast, inspect the Settings row on desktop and phone, run the existing cross-stack checks and record which native desktop paths were exercised. Update the operating and browser specifications to the shipped behavior. |

The first two slices can run together. After they merge, platform delivery and follow-up status can run together if ownership is disjoint. Keep one primary writer and at most one extra worktree. Give shared browser channel changes one owner. Prefer extending existing fixtures and checks. Add an automated case only for a specific regression they miss. Run the browser checks headlessly in a disposable profile. Use recorded adapters for ordinary checks and an isolated OS desktop for native acceptance. After each accepted slice, push main, verify the remote SHA and remove its branch, worktree and disposable output as described in the [roadmap](../roadmap.md#dispatch-and-merge).
