# ReviewQ acceptance

A reviewer should be able to open a review while its native agent is working, read a file without losing their place, give the correct lead feedback and verify what reached that conversation. Exercise the public browser, CLI and native MCP connections using the same production service and the [worked review set](../plans/01-foundation/fixtures.md#worked-review-set). The identifiers below name operator workflows, not a quota for automated tests.

## Workflows

| ID | Action | Required observation |
| --- | --- | --- |
| RUN-1 | Link an already-running native terminal conversation, then find the review from the queue and an ordinary management chat. Open another project with the same MR number. | One registration for the actual provider, session and cwd. The three surfaces agree on the scoped MR/run. A repeat link is idempotent. Ambiguity exposes choices. The unrelated management chat remains ordinary. |
| RUN-2 | Launch a separate review using MCP, preview and launch from the dashboard, open/resume in the terminal, and switch between lead and child. Exercise both supported hosts on the installed build. | Preview is side-effect free. Each launched target retains its requested revision, skill/settings and native acknowledgement. Verify native prompt and identity. Read-only inspection never starts a turn. A provider permission prompt offers handoff to the right terminal. |
| SEND-1 | Send from the Agent composer, then from MCP. Change the selected run with a delayed read in flight. Lose the provider reply after acceptance, reconnect and inspect the existing submission. | Delivered text, stable submission ID, lead/native identity and provider input agree. Exactly one native occurrence per submission, zero at the other lead. Unknown outcomes remain visible until correlated evidence resolves them. A browser toast or HTTP success supplies only its own stage of evidence. |
| HIST-1 | Read above the tail, select text, expand output, page backward, jump to a user prompt, switch to a child and return. Stream updates during reading and across disconnect. | Same native entry, meaningful viewport offset, selection, focus, draft and disclosure state survive applicable updates. At the tail new output follows. Away from it the reader chooses when to return. Gaps recover without duplicated native IDs or wrong-session bodies. |
| DIFF-1 | Open Files, General comments and All conversations. Follow a thread and filter by participant/status. Look at a renamed file, old revision, binary file and unavailable approval rules. | Exact head/base/start refs and old/new path/line agree with the source. No provider mutations result from reading. |
| DIFF-2 | In Active, native Find the unvisited last line, select across three lines, copy into a plain-text target, then read line 820 while discussions arrive at 1060 and 12. ## Browser budgets

Use production assets, the actual local service, and the selected review's normal controls. These are provisional engineering budgets on a named reference desktop. The product owner has **not selected an absolute everyday Chrome tab RAM ceiling**. The controlled renderer comparison below uses frozen reference values. At the first working UI the owner and developer use real measurements to agree on the everyday tab ceiling and check the renderer's responsiveness.

| ID | Measurement and budget |
| --- | --- |
| OPEN | On loopback, fresh browser profile and cold app caches, measure navigation through the first **correct selectable file**, expected inline thread (Quiet displays the loaded empty discussion state), ready fonts and operable controls. For Quiet/Active require p50 ≤1.2 s, p95 ≤2 s. For Large require p50 ≤1.5 s, p95 ≤2.5 s. Also record process startup and cold queue-to-first-usable-row separately. |
| SWITCH | Measure two separate spans for **Active → Quiet → Large → Active**. (1) MR row click → first presented, confirmed Overview with the new MR and operable tabs. Report its distribution. (2) Changes tab activation → first presented, selectable **destination patch** at the correct revision, with usable controls and its expected thread or loaded empty discussion state. Apply p95 ≤500 ms to the Quiet/Active patch and p95 ≤1.5 s to the Large patch, including eviction and return. For **Agent → Changes**, use the same patch budget and require the restored file, logical line and offset. For **Changes → Agent**, measure activation through the restored native entry/body and offset, or the correct live tail. Report that distribution separately. Delayed responses never expose the previous target under a new identity. |
| INPUT | During live updates, measure click/key or committed IME input to the first frame with its correct local result, p95 ≤100 ms. Measure local event publication to first frame with its content, p95 ≤250 ms in steady state. Time to native receipt, source discovery/delivery, reconnect and missed-event catch-up are separate wall-clock intervals. Attribute provider delay and show progress without clearing a draft. |
| FRAME | Across ordinary and Large scrolling, p95 presented-frame interval ≤2 display periods and ≤1% compositor-classified janky scroll frames per measured gesture group. No reproducible visible stutter, blank strip, premature empty state, stale/wrong review frame or anchor jump. Inspect wheel, trackpad, keys, touch where supported, and scrollbar drags/fast flings during a live refresh. On a 120 Hz display two periods are 16.7 ms. Confirm using actual presentation/filmstrip and human input. |
| RAM | Controlled Windows Chrome renderer working-set p50 at 5.5 s must match or improve **137.1 MiB at 1,200 lines and 296.9 MiB at 12,000 lines** on the [reference profile](../plans/01-foundation/fixtures.md#worked-review-set). Publish the raw samples, range and median uncertainty using the recipe below. If a size misses its reference, it can demonstrate a smaller gain only when its upper median confidence limit is below the original observed minimum: 145.80 MiB ordinary or 357.05 MiB large. Record which bar each size met and the size of the difference. Unmatched host/browser/counter/workload makes the historical comparison unverified. Neither lab result establishes an acceptable everyday tab figure. |
| RETAIN | Keep one active patch, zero inactive patch DOMs/raw buffers in app caches, and zero payload fetches for unchanged patch content during unrelated live events. For the active transcript enforce six retained pages/8 MiB, four 64 KiB output ranges per expanded read, 64 navigator groups and two preview pages of up to 50. After warm-up, compare the same quiet return after ten cycles with the return at the end of a 30–60 minute session. Investigate a settled increase above max(20 MiB, 15%) in renderer working set or daemon RSS, growing retained counts or a continuing upward trend across equal cycles. Verify disposal by ownership/heap inspection when process memory remains elevated. |

Use both the byte-exact workload and populated full-product sessions with realistic queue/history, mixed/wrapped code, diagrams and live changes. Rich-session RAM/latency measurements must label their input and counter. Linux renderer RSS, Windows working set, private working set, Chrome tab memory, JS heap, GPU memory and Rust service RSS describe different allocations. Report each in its native unit. A blank-profile control helps interpret process overhead. An artificial low-memory mode, screenshot-only shell or forced-GC reading does not qualify a working review.

**First-milestone renderer acceptance.** Show the owner the headed Chrome tab counter at idle, ordinary, Large, peak and settled return, alongside a live first-open/switch/fast-scroll/send demonstration on the representative machine. Include the cold/switch/typing/scroll results, daemon RSS, frozen comparison where comparable, and features active during the reading. Agree and record an everyday Chrome tab ceiling with its counter, workload and measurement point. Verify the actual reading and perceived responsiveness against that agreement. If RAM or UX misses, revise the renderer at this slice and repeat the affected measurements before expanding the UI. Independent backend work can proceed on the accepted interfaces. Missing historical hardware limits the comparison. Use the retained evidence without rerunning the prior product. ## Shared MCP capacity

One running ReviewQ process and its fixed loopback listeners serve any number of successive authorized native sessions and compatible MCP clients. Independent clients can be idle, read, send, disconnect or reconnect while the browser remains usable. ENTRY defines finite simultaneous work, queue, timeout and response limits. Increasing the number of logical clients must not create persistent ReviewQ processes, native daemons, thread pools, database pools or history observers per client. Growth in sockets for currently connected clients is expected. [Shared service contract](../plans/02-sessions/entrypoints.md)

| ID | Action and required result on the packaged build |
| --- | --- |
| MCP-1 | Establish a one-client control with a genuine authorized Codex chat. Add an authorized Claude chat and ordinary compatible protocol clients to totals of 16 and 64. Include a client that has the appropriate grant and no native provider identity. At each stage mix initialization/discovery, list/get, bounded reads and concurrent browser switching/typing. At the larger stages include a slow consumer. Every eligible client gets service. The two native clients interleave reads and an explicit message to each correctly bound target. Revoke one grant, then verify its next request is rejected and the other still reads and sends under its own grant. |
| MCP-2 | Run at least 10,000 short-lived manager invocations at concurrency 16, including 1,000 reconnect cycles split between 2025-11-25 initialize/initialized then list/get, and 2026-07-28 direct list/get with per-request metadata. Exercise server discovery independently. Hold 32 mixed calls across at least four independent grants (eight active per grant). Across at least eight grants put 64 more into the global wait queue within its two-second deadline, then offer another eligible request. Check global and per-grant limits separately. Pause a response consumer, cancel calls and drop sockets at different stages. Verify documented retryable overload before a new mutation is committed, bounded queues, prompt release of permits, no leaked transactions or duplicate effects. One slow or revoked client cannot starve the browser or ordinary peers. Accepted writes retain their receipts through client loss. |
| MCP-3 | On the 506-registration preset, opening/filtering the queue and reading Changes while agents work in the background causes zero browser-initiated transcript hydrations. Two browser tabs on lead A share one native source observer. The last tab switches to B or closes: release A's browser lease and its observer when no other consumers remain. Trace a genuinely pending report/action lease independently by owner and session. After its completion release that lease too. |

Use an idle-before-load snapshot after process warm-up. At each stage and after 60 s drained, sample PIDs/listeners, native daemons/provider connections, threads/tasks, FDs, DB readers/writer/leases, source readers, CPU, peak and settled RSS, and client/admission queue depth. Mark held slow response and cancellation against the lease/permit readbacks. Capture completed/rejected/timed-out calls by operation and client, p50/p95/max service time and queue wait, with switch and input timings in the concurrent real browser. Lab target at 16 clients, one bounded local status/list/get request per client per second: p95 ≤250 ms for those reads, zero unexpected errors and normal INPUT/SWITCH budgets. At 64 clients, same workload, target p95 ≤1 s for admitted local reads, per-client forward progress, all rejection types accounted for and no silent timeout/replay. Report independent native/provider delay for transcript reads and turns. After drain expect the same set of servers, pools and native connections as the same idle workload, zero request-owned permits, leases and sockets, and no per-cycle retained growth across repeated batches. Reconcile any persistent FDs, tasks or memory delta to a named bounded owner. RELEASE owns this proof on the shipped digest. [Installed qualification](../plans/06-release/release-check.md)

Hold each steady load stage for 60 seconds and stagger client starts. Distinguish logical MCP clients, idle HTTP connections and simultaneously executing tool calls. Use a separate synchronized burst and a deliberately paused read to show the admission bound actually engages. Record one row per client/operation/phase including request time, completion or retry status, secure target alias and whether a durable receipt was created. Use the same scripted input on another checkout if a fairness or cleanup failure needs reproducing.

## Release evidence

Run [the first review](../plans/01-foundation/first-review.md) as soon as the vertical path works. Review each surfaced screen while populated. Execute [browser qualification](../plans/06-release/browser-qualification.md) and [installed qualification](../plans/06-release/release-check.md) on the integrated artifact. For each required case record build/bundle hash, fixture version and input digests, host/browser/display, actual expected/observed values, role performing the check, evidence paths and pass/fail/unverified. Investigate a reproducible functional or visual failure on that revision, fix its owning path and rerun the failed workflow. Identify missing real hardware or host proof explicitly. The independent reviewer must be able to rerun from the tracked instructions and synthetic sources. Measurements, traces, screenshots, native identifiers and release-specific decisions belong in private ignored evidence.

Use the existing checks before adding a case. Admit a permanent test when it would catch a specific regression the current suite misses, such as a cross-run send, overwritten accepted report or selection destroyed by a thread insertion. Prefer a check at the layer that owns the failure and one cross-layer exercise where wiring is the failure. The hard limit is **500 first-party test cases in total**, across Rust and web including integration, browser, unit and executable doctests. Count every parameterized input and generated test case. Inventory runner-discovered cases in the release record and include any runners outside the main commands. Repeated measurement samples and visual fixture generation do not add tests unless registered or run as additional assertion cases. Keep one meaningful workflow through real controls instead of duplicating assertions for each component. [Repository test rules](../../AGENTS.md)
