# Private SQLite storage

The service opens one profile database at `$XDG_DATA_HOME/reviewq/reviewq.sqlite3` (default `~/.local/share/reviewq/reviewq.sqlite3`). A validation runtime resolves a separate absolute path inside its own root. STORE owns the driver, schema, transaction executor and migration registry. Feature adapters in the store crate implement the application’s typed operations. [STORE brief](../plans/01-foundation/storage.md) · [Profile and activation](operations.md)

## Open, migrate and close

1. Resolve a private local filesystem directory owned by the current user (0700), require a regular private file (0600), reject symlink/hard-link and unsafe existing parents targeted by the operation. Apply a private creation mask before SQLite can create the database, WAL, shared-memory or temporary files. Leave unrelated user directories untouched. Refuse a network-mounted WAL deployment. Use a service lock scoped to the resolved database/profile.
2. Probe an existing file read-only before write configuration. An empty database has zero user objects, application ID zero and user version zero. Create in one transaction. The fresh format is `PRAGMA application_id=0x52565132`, `PRAGMA user_version=1`, with a checksum ledger for applied SQL. A foreign application ID, unknown schema, changed applied-step checksum or newer version fails open without mutation. For a recognized format verify its essential tables, columns, indexes, triggers if used, and constraints match the recorded schema. Never adopt an arbitrary populated database with version zero.
3. STORE embeds `crates/store/migrations/0001_initial.sql`. It provisions the v1 relations in the matrix below so parallel feature consumers share one schema. Keep released migration bytes immutable. Each later numbered script has a bundled checksum. For an installed supported older version, normal service open reports the required upgrade to PACK. Under exclusive profile ownership, back up the quiesced database and apply upgrades to a separate private candidate. Use `BEGIN IMMEDIATE`, re-read the current version, run pending SQL and structural/foreign-key checks, then commit checksum and new user version with each step. Only PACK activates the verified candidate. On interruption only committed steps count. Compare restored byte/semantic evidence before resuming the service. A known transfer source follows the explicit candidate procedure. [SQLite backup](https://www.sqlite.org/backup.html) · [Transfer](../plans/06-release/transfer.md)
4. Use bundled rusqlite with the backup feature. Enable and check foreign keys on **each** connection, WAL once on the writer, `synchronous=FULL` on the writer, 2 s busy timeout and read-only/query-only reader connections. One dedicated writer thread and one separate reader thread each own a connection. Each has a bounded Tokio channel (64 jobs) and request/oneshot replies. Full channels fail fast as `busy`. Bounded batch reads return owned data, then release their read transaction before waiting on the caller. Serve large immutable artifacts in ordered chunks so a slow browser cannot pin a DB reader, writer or old WAL snapshot. [WAL semantics](https://www.sqlite.org/wal.html) · [Connection API](https://docs.rs/rusqlite/latest/rusqlite/struct.Connection.html) · [Tokio bounded channels](https://docs.rs/tokio/latest/tokio/sync/mpsc/index.html)
5. Closing rejects new admissions, drains accepted DB work to a deadline, joins workers and checkpoints when readers permit. Native delivery/recovery uses durable receipts across abrupt death. File backup/transfer/promotion and service activation use exclusive profile ownership and closed, verified candidates. [Operations](operations.md)

## V1 relation inventory

The table lists physical relation names, required keys and data needed by first callers. Use integer primary keys internally where helpful. Public identifiers round trip exactly. Index each child FK and the listed paging keys. Scope external IDs by provider instance. UTC times use signed Unix milliseconds in SQLite and wire timestamps in UTC. Git SHAs, receipt IDs and content hashes retain their full validated text. Use checked JSON for structured bounded data, with typed readers and a format version for evolving payloads. Store large accepted documents by chunks.

## Reads, mutations and external effects

| Use case | Commit boundary and losing race |
| --- | --- |
| Read and subscribe | Start a short deferred read transaction, establish the snapshot, read the requested projection and the event head on the same connection. Return that head with the projection. An external native read uses separately validated generation/provenance. |
| Register or send | Re-authorize the stable actor, target and active grant. Check existing receipt before preconditions. Same normalized request returns the saved identity/result; changed content under the same id yields conflict. Check run/lead and expected revision; insert intent, receipt and resource event together. After commit, wake delivery. Claim using conditional state/fence then make native call outside SQL. On missing proof record uncertain and reconcile that same native submission. |
| Refresh or settings | Validate providers outside SQL under one settings revision. Commit new observations, checkpoint, last-good pointer, notification occurrences and events together. Refuse an overtaken result. Settings activation swaps config and bound secrets, revokes stale grants, and records desired projection revision atomically. Reconcile installed files afterward. |
| Report capture | Stage immutable chunks under a private candidate in bounded transactions. During streaming compute/report statistics and SHA; verify native evidence, stable file identity, length, hash and exact UTF-8. Seal only complete input. Final short write checks run, parent/version/disposition, batch and grant. Promote accepted artifact reference, semantic receipt and notification, and complete matching batch/coverage together. On failure retain previous head. Reclaim abandoned unreferenced stage chunks by indexed age after recovery has checked candidates. |
| Follow-up dispatch | Adopt deduplicated observations and schedule/freeze against the exact monitor generation, current human state, global capacity, source revision and base receipt. Reserve capacity, persist frozen manifest, and create its outbox receipt in one transaction. A stale worker cannot adopt an observation or finish a superseding batch. |
| Read notification or handle review | Inbox read/dismiss changes explicit notification IDs. A review decision/checkpoint advances only the captured per-review evidence after a fresh source-head check. Independent revision/facet changes receive their own invalidations. |

Every user-visible write records one or more scoped invalidations with the mutation, then publishes a *wake-up* to live readers after commit. A duplicate receipt/occurrence adds no duplicate effect. Failure before commit rolls back all facts and the event head. Death after commit and before wake-up is recoverable by querying the durable journal. For an external effect that cannot confirm its outcome, preserve uncertainty across restart and require evidence before retry. ## Resource lifetime

Keep the newest 4,096 global invalidation rows; trim in bounded indexed batches during normal writes, updating replay floor atomically. Retain a stable independent event head across trimming. Preserve accepted versions, exact authority/receipts and registered bindings until a separately designed deletion or explicit user action. Idle session records require disk space only. Native reader caches, subscriber queues, patch documents, staging and scratch files have independent bounded lifetimes. SQL pages use stable keysets and captured generation/watermark; changed filter/scope invalidates a continuation. Measure actual query plans, idle service threads/handle counts, WAL file size after reader cancellation and worker queue pressure on the worked/busy fixture. [Qualification workloads](acceptance.md)
