# Private SQLite storage

The service opens one profile database at `$XDG_DATA_HOME/reviewq/reviewq.sqlite3` (default `~/.local/share/reviewq/reviewq.sqlite3`). A validation runtime resolves a separate absolute path inside its own root. STORE owns the driver, schema, transaction executor and store-open probe. Feature adapters in `reviewq-store` implement the application’s typed operations. [STORE brief](../plans/01-foundation/storage.md) · [Profile and activation](operations.md)

Accepted Findings can also have a disposable sibling cache named `<database>.findings-display`. It holds derived spans or a fallback reason, keyed by sealed artifact, SHA-256 and display-format version. It stores no authored report bodies. The cache uses a separate SQLite application ID and is bound to the authoritative store identity. A missing or unusable cache cannot prevent opening the profile or accepting a report. The database file is capped at 16 MiB. Retention removes old entries on publication, with up to 32 retained index entries across formats and a 30-day age threshold. A rollback can reopen the authoritative database independently. [Indexed Findings](../plans/05-browser/indexed-findings.md#implemented-scope)

## Open and close

1. Resolve a private local filesystem directory owned by the current user (0700), require a regular private file (0600), reject symlink/hard-link and unsafe existing parents targeted by the operation. Apply a private creation mask before SQLite can create the database, WAL, shared-memory or temporary files. Leave unrelated user directories untouched. Refuse a network-mounted WAL deployment. Use a service lock scoped to the resolved database/profile.
2. Under the profile lock, exclusively create a new database only at an absent path. Initialize it in one transaction with the embedded current schema, application ID `0x52565132` and format ID (`user_version`) 2. Expose it at its final path only after initialization commits. On interruption, clean up only positively identified, operation-owned staging files.
3. For an existing path, check the application ID, exact format ID and expected table, column, index, constraint and trigger definitions against the build’s one embedded schema from `crates/reviewq-store/src/schema.sql` and its feature SQL files under `crates/reviewq-store/src/schema/`. Probe read-only before configuring a writer or changing SQLite settings. Reopen a matching store with its existing records. An empty, foreign, damaged or unrecognized file remains untouched, including sidecars. Report its path and the reason. Use SQLite’s backup API for a coherent recovery snapshot. [SQLite backup](https://www.sqlite.org/backup.html)
4. Use bundled rusqlite with the backup feature. Enable and check foreign keys on **each** connection, WAL once on the writer, `synchronous=FULL` on the writer, 2 s busy timeout and read-only/query-only reader connections. One dedicated writer thread and one separate reader thread each own a connection. Each has a bounded Tokio channel (64 jobs) and request/oneshot replies. Full channels fail fast as `busy`. Bounded batch reads return owned data, then release their read transaction before waiting on the caller. Serve large immutable artifacts in ordered chunks so a slow browser cannot pin a DB reader, writer or old WAL snapshot. [WAL semantics](https://www.sqlite.org/wal.html) · [Connection API](https://docs.rs/rusqlite/latest/rusqlite/struct.Connection.html) · [Tokio bounded channels](https://docs.rs/tokio/latest/tokio/sync/mpsc/index.html)
5. Closing rejects new admissions, drains accepted DB work to a deadline, joins workers and checkpoints when readers permit. Native delivery/recovery uses durable receipts across abrupt death. Installation and recovery coordinate through the profile lock. Verify a recovery backup before use. [Operations](operations.md)

## Relation inventory by first use

The table describes the intended integrated schema. Each implementation brief updates the current schema alongside its first caller. Use integer primary keys internally where helpful. Public identifiers round trip exactly. Index each child FK and the listed paging keys. Scope external IDs by provider instance. UTC times use signed Unix milliseconds in SQLite and wire timestamps in UTC. Git SHAs, receipt IDs and content hashes retain their full validated text. Use checked JSON for structured bounded data, with typed readers and a format version for evolving payloads. Store large accepted documents by chunks.

## Reads, mutations and external effects

| Use case | Commit boundary and losing race |
| --- | --- |
| Read and subscribe | Start a short deferred read transaction, establish the snapshot, read the requested projection and the event head on the same connection. Return that head with the projection. An external native read uses separately validated generation/provenance. |
| Register or send | Re-authorize the stable actor, target and active grant. Check existing receipt before preconditions. Same normalized request returns the saved identity/result; changed content under the same id yields conflict. Check run/lead and expected revision; insert intent, receipt and resource event together. After commit, wake delivery. Claim using conditional state/fence then make native call outside SQL. On missing proof record uncertain and reconcile that same native submission. |
| Refresh or settings | Validate providers outside SQL under one settings revision. Commit new observations, checkpoint, last-good pointer, notification occurrences and events together. Refuse an overtaken result. Settings activation swaps config and bound secrets, revokes stale grants, and records desired projection revision atomically. Reconcile installed files afterward. |
| Ledger write and publish | Each ledger call is one short transaction: check the caller binding, the expected revision and the limits, then write the record, its change row, the ledger sequence and the call result together. Publishing reads the records and the sequence, composes the text and its statistics and SHA outside SQLite, then one short write checks the sequence, run, parent/version/disposition, batch and grant. It seals the chunks, appends the version, advances the head, closes the pass, and saves the semantic receipt, notification and matching batch/coverage together. On failure retain the previous head and every record. |
| Follow-up dispatch | Adopt deduplicated observations and schedule/freeze against the exact monitor generation, current human state, global capacity, source revision and base receipt. Reserve capacity, persist frozen manifest, and create its outbox receipt in one transaction. A stale worker cannot adopt an observation or finish a superseding batch. |
| Read notification or handle review | Inbox read/dismiss changes explicit notification IDs. A review decision/checkpoint advances only the captured per-review evidence after a fresh source-head check. Independent revision/facet changes receive their own invalidations. |

Every user-visible write records one or more scoped invalidations with the mutation, then publishes a *wake-up* to live readers after commit. A duplicate receipt/occurrence adds no duplicate effect. Failure before commit rolls back all facts and the event head. Death after commit and before wake-up is recoverable by querying the durable journal. For an external effect that cannot confirm its outcome, preserve uncertainty across restart and require evidence before retry. [Event replay and cursor limits](data-contracts.md#global-event-stream) · [Workflow](review-workflow.md)

## Delivery worker

A retained message can have a last known state of `queued` even when the service has no authority to send it. History reads the message by its run and session. Dispatch reads due intents, joins the selected message, claims it under a fence, and calls the native host after commit. A fresh send creates the intent in the same transaction as the message. A repeated submission returns the existing receipt. Reconciliation updates the outcome only on new evidence.

A single table with a partial index on message status would still require an independent authority condition. Keeping a second copy of each message in an archive would add a second payload and read path. A narrow intent keeps the worker index proportional to outstanding work while the message has one durable identity. Queue the worker on a post-commit wake or the nearest retry deadline, and recover outstanding intents in bounded batches at startup. SQLite supports indexes limited to eligible rows. The transactional outbox pattern requires the intent to commit with the message and accounts for duplicate delivery. [SQLite partial indexes](https://www.sqlite.org/partialindex.html) · [Transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

## Resource lifetime

Keep the newest 4,096 global invalidation rows; trim in bounded indexed batches during normal writes, updating replay floor atomically. Retain a stable independent event head across trimming. Preserve accepted versions, exact authority/receipts and registered bindings until a separately designed deletion or explicit user action. Idle session records require disk space only. Native reader caches, subscriber queues, patch documents, staging and scratch files have independent bounded lifetimes. SQL pages use stable keysets and captured generation/watermark; changed filter/scope invalidates a continuation. Measure actual query plans, idle service threads/handle counts, WAL file size after reader cancellation and worker queue pressure on the worked/busy fixture. [Qualification workloads](acceptance.md)
