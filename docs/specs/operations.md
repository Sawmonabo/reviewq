# Installation, updates and recovery

ReviewQ runs as a personal Linux or WSL2 application. One Rust executable serves the production browser and accepts terminal commands. The installed directory includes version-matched web files and native host assets. An installed user service continues polling after the terminal closes. A foreground validation process can run alongside it in a separate private directory.

## What the operator runs

| Command | Observable result |
|---|---|
| Bundled `bin/reviewq install --from /absolute/release` | Verify the local bundle, install or update the user's managed launcher and service, provision the native assets and print the active build and dashboard address. A fresh install opens first-run setup on first visit. An ordinary upgrade reuses the current supported data. |
| `reviewq` or `reviewq open` | Repair the [start door](#start-door), then start or reuse the service, wait for the exact installed profile to become ready and open its dashboard. Print the local dashboard URL if browser handoff fails or with `--print-url`. Repeated opens reach one service. |
| `reviewq start`, `reviewq stop` | Start/resume or stop local monitoring. A repeated request is safe. Report the resulting service state. Start repairs the [start door](#start-door) first. Stop stops only the service; the start door keeps listening, so the stopped page's Start button keeps working. Neither changes whether ReviewQ starts at login. `reviewq.service` has no start limit (`StartLimitIntervalSec=0`), so quick Quit and Start cycles never block a start; `Restart=on-failure` already waits 5 seconds between restarts. A start the user manager refuses says to inspect `reviewq logs`, which has the reason. Existing Claude and Codex sessions continue under their native hosts. |
| `reviewq status`, `reviewq refresh` | Status reports running state, last successful synchronization, current failure/refresh and queue counts. Refresh waits for the requested/coalesced refresh result. A failure or bounded wait expiry reports which result remains pending. These commands use the same profile and application state as the browser. |
| `reviewq logs`, `reviewq notify-test` | Show recent sanitized service/UI failures, including those of the [start door](#start-door)'s connections, such as a start that failed, or send one labeled local test notification and report the OS handoff result. A missing desktop facility is visible. WSL uses the user's owned ReviewQ Windows sender; Linux uses the desktop notification service. |
| `reviewq serve [--port N]` | Run in the foreground using installed paths, exit cleanly on termination, and refuse a second writer for the same profile. The service unit invokes this entry. |
| `reviewq serve --validation --runtime-root /absolute/private/path [--port 8768]` | Serve the production API and web build against private disposable data. Disable provider polling, launches, sends, corrections, follow-up dispatch, notification delivery and personal host/service installation. Use seeded data for inspection. Real native and provider proof uses a separately installed disposable account. |
| `reviewq uninstall [--delete-data]` | Stop and disable the start socket, then disable/stop the owned service and remove owned application and host registrations. Print retained data paths and any user-edited entries requiring attention. A later install reopens whatever store the data folder then holds. When the record still names a store, as after a `--delete-data` uninstall that removed the installation and was then refused or interrupted before deleting, an install that finds a different store or none says so and uses the folder as it is. With `--delete-data`, once every removal step has succeeded, delete the [owned data](#owned-data) and print what was deleted and anything kept, with the reason. |

Run the installed binary from any directory. Loading the browser, using the MCP tools in an ordinary chat and starting a review session are independent actions. The native skill, registration, report, publication, acknowledgement and management command behavior belongs to [native sessions](agent-sessions.md) and [ENTRY](../plans/02-sessions/entrypoints.md).

## Installation and local identity

Use an active systemd user manager for the background installation, a compatible browser and configured native host executables for the integrations selected for use. Verify which OS, architecture, loader, host versions and desktop/WSL interop were exercised with each released artifact. Rust, Node, pnpm and `readelf` are build tools. The packaged Rust server and Claude's host-loaded JSX use the installed binary and provider CLIs at runtime. Building the web UI stays separate from normal Rust compilation. [systemd services](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html) · [Production bundle](https://vite.dev/guide/build.html)

| Personal location | Content and ownership |
|---|---|
| `~/.local/bin/reviewq` | Stable launcher pointing into the active release. Its target is absolute and can be invoked by native hooks independent of shell PATH. |
| `$XDG_DATA_HOME/reviewq/{current,releases,previous-assets}` | Private installation root with an atomic link to the active immutable bundle. After an update it keeps only the active complete bundle and any changed fingerprinted files from the preceding web build that an already-open tab may still load. |
| `$XDG_DATA_HOME/reviewq/reviewq.sqlite3` | Current STORE database. SQLite application ID `0x52565132`, current format ID 1. Keeps workflow state, versioned settings, private provider credentials and receipts. The service opens this path after verifying its supported format. Retain it across uninstall. |
| `$XDG_CONFIG_HOME/systemd/user/reviewq.service` | Managed user unit. Starting an installed service opens no browser. Stop/disable via the systemd user manager when removing it. |
| `$XDG_CONFIG_HOME/systemd/user/reviewq-start.socket`, `reviewq-start@.service` | The [start door](#start-door): the socket and the template each connection runs. The installer renders both from the current browser port and installed executable; neither has an install record entry. A file is ReviewQ's when its first line is the start door's marker line, and ReviewQ rewrites it whenever it differs, so edits are overwritten. Any other file at either path is preserved and reported. |
| `$XDG_CONFIG_HOME/reviewq/` | Private runtime options and native bridge descriptor. Installed callbacks read `bridge.json` with the installation ID, canonical native address, browser URL and scoped secret. Generate it under owner-only permissions. A terminal skill, command line, log, browser asset or output receipt never contains this credential. |
| `$XDG_STATE_HOME/reviewq/` | Private operational state, retained backups, install journal, stable install/profile lock inodes and sanitized local diagnostics. A lock stays outside any path removed by an update or uninstall. |
| Native host state | The explicit Codex registration skill links under the selected Codex user directory. The Claude marketplace/plugin installs at user scope using the host CLI. Configured checkouts/worktrees receive the separate management skill and exact private MCP grant through ENTRY. Provider sign-in, native histories, preferences and unrelated plugins remain with the native host. |

Resolve unset XDG config, data and state homes to `~/.config`, `~/.local/share` and `~/.local/state`. Honor absolute overrides. Use private owner directories (0700) and files (0600) for state and credentials. Shared parent directories stay under their current owner/mode. Open private files with checked ownership, link type and exclusive creation where appropriate. Installed and validation data/credential paths are disjoint including symlink, hard-link and SQLite sidecar aliases. [XDG base directories](https://specifications.freedesktop.org/basedir/latest/)

Use `http://127.0.0.1:8766` by default for the browser. Any local browser profile can open the running service's dashboard or a saved review link directly. The browser obtains its write proof automatically when needed. When IPv6 loopback is available, bind `[::1]` on the next port for native Linux clients in WSL and record the actual endpoint in the private descriptor. Otherwise use the verified IPv4 loopback for native clients. Validate the configured base port and both bindings before opening writable state. An occupied port yields a conflict, closes any partially acquired listener and preserves its owner. A private validation port pair must be separate from both installed ports. Apply the shared HTTP/MCP authentication and origin rules at the corresponding listener. After verifying the unit/profile owns the bound listener, perform the challenge-authenticated `GET /api/v1/status` and verify its signed response before trusting build digest, installation/profile identity, store support and queue readiness. All listeners are loopback-only. [Browser launch and service readiness](data-contracts.md#browser-launch-and-service-readiness)

## Configure the local runtime

The installed nonsecret file is `${XDG_CONFIG_HOME:-$HOME/.config}/reviewq/runtime.json`. Print this resolved path in the install receipt and in `reviewq status`, including when the user service is stopped. PACK creates it privately on first install, retains it on update/uninstall, and reads it before activating provider hosts. The service reads one validated snapshot at startup.

| Property | Default, validation and use |
|---|---|
| `port` | Integer 1024–65531, default 8766. Bind browser IPv4 loopback and the optional IPv6-native port at base + 1. The installed start door uses base + 4. An explicit foreground `serve --port N` selects that invocation's base. Installed `serve` otherwise uses the file. Validation uses its explicit port, otherwise 8768, and its own private configuration. Never rewrite the saved port from a temporary CLI override. |
| `pollSeconds` | Integer ≥60, default 300. Time between scheduled provider refreshes while connected. A manual refresh still runs through the shared refresh coordinator. Changing the interval does not acknowledge events or change the last successful refresh. Use a checked timer conversion; reject a value beyond the scheduler's representable range. |
| `desktopNotifications` | Boolean, default true. Automatic delivery first offers an eligible notification to one connected browser with permission. When the browser cannot accept the offer, ReviewQ uses the local desktop sender. An unconfirmed display authorization leaves an uncertain receipt. False mutes automatic desktop delivery while recording inbox events, unread counts, deduplication and normal agent/report state. After re-enabling, apply the normal unread, dismissal, grouping and already-notified rules. Explicit `reviewq notify-test` still sends one labeled diagnostic. |
| `claudeCommand`, `codexCommand` | Nonempty executable names/paths. Defaults resolve from the installed account's home as `~/.local/bin/claude` and `~/.local/bin/codex`. Prefer literal absolute paths in the file. Resolve a bare command using the service PATH, record the effective executable for the operation, and pass arguments separately. A missing executable identifies the unavailable integration; never substitute another provider or account. Provider-native profile selection uses `CLAUDE_CONFIG_DIR` / `CODEX_HOME` in the installed service environment, then the respective host defaults. Do not use a caller's cwd to choose a different profile. |
| `chromiumCommand` | Optional local Chromium executable name or absolute path. ReviewQ uses it with a disposable private browser profile to prepare verified completed Mermaid drawings. Validated drawings stay available until they expire. The reader uses its built-in Mermaid renderer when a matching saved drawing is unavailable. |
| `wslDistribution` | String. A nonempty explicit distribution wins for Windows Terminal handoff. Otherwise use the current WSL distribution from `WSL_DISTRO_NAME`. During installation on WSL, capture the detected distribution as the initial value so a user service without the shell environment can reopen the same distribution. If neither source supplies it, return the exact native copy command. On Linux the option is unused. Pass the selected name as one `wsl.exe --distribution` argument. |

On the installed dashboard, **Notifications → Enable browser alerts** requests the browser’s notification permission. While an eligible ReviewQ tab is connected, its browser displays the alert. Clicking it focuses a compatible ReviewQ tab and opens the exact inbox item. With several tabs, the most recently focused compatible tab takes the click. Closing every tab after display lets the click open one new tab. When the service issues an alert with no eligible browser, the native notifier carries the same inbox link. Windows and Linux pass that link to the default browser, which chooses the tab. A possible display whose acknowledgement was lost keeps its uncertain receipt.

For example, a WSL user whose tools are installed under `/opt/local/bin` can save the following as `runtime.json`. The settings use a three-minute poll and mute desktop pop-ups. The browser will use `127.0.0.1:8910` and the native IPv6 endpoint, when available, will use port 8911.

```json
{
  "port": 8910,
  "pollSeconds": 180,
  "desktopNotifications": false,
  "claudeCommand": "/opt/local/bin/claude",
  "codexCommand": "/opt/local/bin/codex",
  "wslDistribution": "Ubuntu-24.04"
}
```

For a manual edit, save in the same private directory with mode 0600 using an editor with atomic replace, then run `reviewq stop`, `reviewq start` and `reviewq status`. Stop must work through the verified user unit even when the file is invalid. Each start validates the whole object, applies defaults for omitted fields and fails with the path and offending property on invalid JSON, unknown keys, wrong types or impossible port pairs before claiming a writable store. The browser, native and start ports must all differ. Active settings stay at the previous startup snapshot until restart. A failed restart is visible via status/logs; correct the file and start again. PACK updates it only by exclusive private temp, flush, atomic same-directory rename and parent sync, after comparing the expected original to avoid overwriting simultaneous user edits.

After a port or native profile change, republish the verified bridge locator and reconcile checkout MCP endpoints through ENTRY with the currently committed settings revision. If the port changes, open the new address reported by `reviewq open --print-url`. The start socket follows the new port at the next start with no further step. An app installed from the browser is tied to its address, so reinstall it from the new address. At the same address, an open tab can keep its selection while recovering from a service restart. A tab from the preceding distinct web build can still fetch its fingerprinted files. Updates with identical web files keep that same compatibility set. A tab from an earlier build may need an ordinary reload to load a previously unopened view. ReviewQ leaves that reload to the user so they can finish or copy any in-memory draft first. Installed command and host clients discover the verified active listener from its private locator. An unsaved or not-yet-applied port edit cannot redirect a native call. Test a restart with the requested pair occupied and check that the service reports the conflict and the unrelated listener receives no bearer.

Interactive **Settings** saves apply through SQLite. PREFS owns accounts, repository bindings, credentials and the independent Codex recovery preference. FOLLOW owns automatic follow-up policy, per-MR overrides and the shared review concurrency (default 2, range 1–8). Recovery and automatic follow-ups start off. These changes use their own versioned compare-and-set operations and apply without a service restart. The service rejects automation-policy keys in `runtime.json` and points to the matching Settings controls. [Settings](queue-and-settings.md)

## Dashboard controls

**Settings → App → System** shows the version, how ReviewQ runs (`installed` for the managed service, `foreground` for `reviewq serve`, `validation`), the dashboard address, the data folder, the size of the [owned data](#owned-data) and the last successful refresh, which is left unknown when the source cannot load so the page and its controls still show. The installed service also offers the login switch, Quit and Uninstall. Each of the three is a browser mutation with the exact Host, dashboard Origin, same-origin fetch metadata and the browser write proof. Each is refused with `409` and a sentence the page shows when the server is not the installed service ("Available in the installed app.") or when an install, update, uninstall, start or stop holds the installation lock ("An install or uninstall is running. Try again when it finishes."). The lock is tried without waiting.

| Control | Effect |
|---|---|
| **Start when I log in** | `systemctl --user enable` or `disable reviewq.service`, without `--now`, then reply with the state read back. It never starts or stops ReviewQ now. A first install turns it on; an update keeps it as the user left it, and a rollback restores the recorded state. The start door stays enabled either way. |
| **Quit** | Reply `202` and, in a task of its own that a closed browser connection cannot cancel, run `systemctl --user --no-block stop reviewq.service` under the installation lock. The stop signals every process in the service, that command included, so ReviewQ's own stop signal is what shows the stop is under way. The listeners finish their open replies. If no stop signal arrives within 2 seconds, because systemd could not be asked or does not run this process, ReviewQ logs why and exits by itself with status 0, which `Restart=on-failure` does not restart. ReviewQ stays stopped until the stopped page's Start button or, with the switch on, the next login. |
| **Uninstall** | Make the uninstall's checks in the service, then hand the work to a job outside it, since stopping the service ends every process in it. Reply `202` with no body. |

The uninstall checks, shared with `reviewq uninstall`: the install journal has no pending activation, the service unit on disk is the installed one, and the start door files are ReviewQ's. The dashboard also refuses while a `reviewq-uninstall` job is running. A failed check is the `409` sentence; any other failure is logged and answered as an internal error, with nothing from it in the body. The job is the transient user service `reviewq-uninstall`, collected after it ends, running the release's own executable as `reviewq uninstall --expect-store <store ID> [--delete-data]` with exactly the environment the installed unit sets. The fixed unit name refuses a second job while one runs. With `--expect-store`, the job fails unless the install record names that store, so a job that resolves another state folder never reports an empty removal as success. Its output is in the user journal under `reviewq-uninstall`. On any failure it sends a desktop notification, "ReviewQ couldn't finish uninstalling: <reason>.", with the one step left, repeating `--delete-data` when it was asked. When it finishes but leaves anything in place, such as a Codex hook entry the user changed or a kept data entry, it sends one notification, "ReviewQ is uninstalled, but left in place: <up to three, and how many more>.", and points to the journal for the reasons. Both go through the Windows sender while it is still registered, otherwise `notify-send`. The Windows notification identity is removed last, after any data deletion, so it can report everything before it; a data deletion refused once ReviewQ itself is removed sends its failure notice first, then removes the identity; when entries were already reported, a Windows identity that then cannot be removed adds no second notification. When Windows cannot remove it, the uninstall reports it and finishes; the install record keeps it, and the message says that the next install reuses it and that running `bin/reviewq uninstall` from a ReviewQ release folder tries the removal again, since the launcher is gone by then. Once it is removed, a record left holding nothing is deleted. `reviewq uninstall` and the job end by listing everything left in place. They exit with an error only when removing something failed, such as the Windows identity or an entry that could not be read or removed; an entry kept by rule, such as a link, another user's file or a hook entry the user changed, leaves nothing to retry, so it is listed and the exit status is 0. While the launcher exists, `reviewq uninstall` finishes anything left, and `reviewq install` finishes an interrupted uninstall, keeping the data, before it installs.

### Start door

`reviewq-start.socket` holds `127.0.0.1:<browser port + 4>` with `Accept=yes` and `TriggerLimitIntervalSec=0`, wanted by `sockets.target`. With no trigger limit a burst of connections cannot put the socket in a failed state, where it stops listening; older systemd has no poll limit to slow a burst first. `MaxConnections`, 64 by default, still bounds how many door processes run at once. For each connection systemd starts one instance of `reviewq-start@.service`, which runs `reviewq start-door` with the connection as standard input, sends its output to the journal, and is stopped after 10 seconds at most. The stopped page's Start button works with no ReviewQ process running, and any number of stray connections only start short-lived door processes, and `reviewq.service` has no start limit for them to reach. The dashboard port is never socket-activated: visiting the address while stopped never starts ReviewQ.

Both files begin with the same fixed marker line, `# ReviewQ start door. ReviewQ rewrites this file; edits are lost.`, and that line alone decides ownership. A missing file is written; a file whose first line is the marker is rewritten whenever its bytes differ from the current render; any other file at either path is preserved and reported, and the install, uninstall or repair refuses.

`reviewq start-door` reads no settings, store or install state and takes no lock. It answers one HTTP/1 request, with a 2-second limit for the headers, no keep-alive and a 5-second limit in all. A valid start is `POST /start` with Host `127.0.0.1:<start port>` and Origin `http://127.0.0.1:<browser port>`, the browser port being the start port minus 4. It gets `204`, and the door then runs `systemctl --user --no-block start reviewq.service`; a start asked for during a stop, a Quit included, runs after the stop. The stopped page repeats its request every 3 seconds until the dashboard answers, which covers a request made before the stop began; a repeated request while ReviewQ runs changes nothing. Every other request gets `404`, without CORS headers, and starts nothing. The door exits with status 0 either way; a failed start is one journal line. Foreground and validation servers have no start door.

| Operation | Order |
|---|---|
| Install, update, rollback | Stop the socket and any door still answering a connection, stop the service, write the units, reload the user manager, enable and start the socket, then start the service. A socket that cannot listen is reported and repaired at the next start; it does not stop the activation. A rollback first asks the previous release's own program whether it has the door, by running its `start-door --help`, which exits 0 only where the command exists; a program that fails to answer within 5 seconds counts as having none. A rollback to a release that has the door puts it back at once, whether or not ReviewQ was running: it stops the socket and any door, writes both files, and enables and starts the socket after the reload. When the files cannot be written, such as for a foreign file at a door path or an unreadable `runtime.json`, the rollback leaves the socket stopped, says "ReviewQ's Start button will not work until its next start: <reason>" and finishes; the repair at the previous release's next start tries again. A rollback to a release from before the door, which has no `start-door` command and would never remove it, stops and disables the socket and removes both files instead. The install record holds no field for this, since an older release refuses a record with a field it does not know. |
| Uninstall | Stop the socket and any running door, disable the socket, then remove the service and everything else, including both door files. |
| Quit, `reviewq stop` | Stop the service only. Both ask systemd for the stop; `reviewq stop` waits for it. |
| `reviewq start`, `reviewq open`, every installed start | Repair the door, then start the service. The service repairs it after its dashboard is ready. |

The repair renders both files for the current `runtime.json`. When either differs it stops the socket, writes the files and reloads the user manager; when a later step fails it still tries to start the socket before reporting the failure. It enables the socket, clears a failed state, such as a hit start limit, and starts it when not listening. This works while `reviewq.service` runs. The service's own repair first looks, without the installation lock, whether the files differ or the socket is disabled or not listening; only then does it ask for the lock, so a sound door never makes the System page refuse a change. While an install or rollback holds the lock it asks again every 2 seconds for up to 2 minutes; after that the next start repairs. A restart of the user manager starts the socket again through `sockets.target`.

### Owned data

One list in the installer names what the current code writes. The System page's size and `--delete-data` both read it, and the size counts exactly what a deletion removes: a folder removed only when empty adds nothing. Sizes and deletion never follow a link. Deletion refuses links and entries another user owns, including a ReviewQ folder that is itself a link, which it keeps and reports, removes a folder only once it is empty, and then removes each ReviewQ folder left empty. A ReviewQ folder that still holds an entry not on the list is kept and reported, "Kept <folder> because it holds files that are not ReviewQ's.", with exit status 0; one that holds only entries already reported, the install record or `install.lock` needs no line of its own.

| Folder | Owned entries |
|---|---|
| `$XDG_DATA_HOME/reviewq` | `reviewq.sqlite3` and its `-wal`, `-shm` and `-journal`; `reviewq.sqlite3.findings-display` and its `-journal`; `service.json` and `.service.*`; `.reviewq-stage-*`; `diagram-cache/`; `diagram-jobs/`; `checkout-grants/`; the empty `releases/` folder an uninstall leaves |
| `$XDG_CONFIG_HOME/reviewq` | `runtime.json` |
| `$XDG_STATE_HOME/reviewq` | `install.json` and `codex-hooks.json`; `install.lock` last of all, as below |
| Any of the three | `.reviewq-write.*` and `.reviewq-link.*` left by an interrupted write |

Deletion refuses while ReviewQ's unit or launcher is still in place, since a record that names no installation then belongs to another state folder; it says to run the command with the `XDG_STATE_HOME` ReviewQ was installed with. Whenever the data folder exists, the uninstall takes the store's own profile lock first, which proves nothing still has the database open, and checks that any store there is the installed one, by the ID captured before the install record was reset. When the lock is held it deletes nothing, or nothing more when an earlier attempt began the deletion, and says which process to stop; a different store is refused the same way. A removal step that failed deletes nothing. A Codex hook entry the user changed is reported as a warning and does not stop the deletion. The record keeps the store ID. Only once these checks pass and the store's lock is held does it mark the deletion, until the data is gone, and it is deleted last, so an interrupted deletion resumes with the same check: the next `reviewq uninstall` finishes it, and `reviewq install` finishes it before installing. A refused deletion leaves the record unmarked, so a later install or uninstall keeps the data. The two refusals that come after ReviewQ itself is removed, another process holding the store or a different store in the data folder, leave no launcher to run again: ReviewQ is uninstalled, its Windows notification identity is removed as a keep-data uninstall removes it, the data is kept, and the refusal names the folders to delete by hand. A deletion already under way when it is refused stays marked, so the next `reviewq install` finishes it before installing. An entry the deletion could not read or remove makes `reviewq uninstall` exit with an error naming it; one kept by rule is listed and does not. Files the current code never writes, including those left by earlier versions, stay, and so does their folder. Once the record is deleted, `reviewq uninstall`'s last act deletes `install.lock` while it still holds the lock, then the state folder when that leaves it empty. Each process that takes the lock checks, once it holds it, that its open file is still the one at that path, and otherwise locks again, so one that waited through the deletion never shares the lock with the next. A keep-data uninstall keeps the file, and so does `reviewq install` when it finishes an interrupted uninstall, since it goes on installing under that lock.

## Data choices on install

| Starting point | Result |
|---|---|
| Absent database | Initialize the current schema in a new private file and open setup. New credentials are scoped to this installation. |
| Current-schema store, including a retained profile after uninstall | Reopen it, verify the binary, assets and readiness, and preserve settings, report versions, unread events, pending submissions and native identities. |
| Unrecognized file or user-owned destination | Report the conflicting path before switching the launcher or activating host assets. Preserve the file and its sidecars. |

## Recovery and removal

Hold a kernel-managed advisory lock for competing install, uninstall and release recovery operations. The daemon holds a separate lifetime lock for a specific data profile. Lifecycle requests use the user manager and the install journal to avoid a second writer during the switch. Use unique private sibling candidates, durable intent before each external effect, digest/ownership readback after it and atomic same-directory rename of each published pointer. The journal coordinates multi-file and native-host updates. An install is ready only after the service identifies its build/profile and the recorded host activations have been read back. After that check, retire verified bundles other than the active one, remove obsolete owned asset copies, and keep the single preceding web compatibility set. The first migration from the older installer uses its nearest verified distinct web bundle when legacy records cannot identify the last successful switch. Preserve and identify modified or unrelated entries. Subsequent invocations can finish interrupted steps. [Rust file locking and sync](https://doc.rust-lang.org/std/fs/struct.File.html) · [SQLite backup](https://www.sqlite.org/backup.html)

| Interruption or failure | Next invocation |
|---|---|
| While staging or checking a manifest | Existing installation serves the last complete release. Discard or reuse only the current operation's private candidate after rechecking it. Publishing a contradictory candidate requires a new output. |
| After switching a pointer, before host/service readiness | Reacquire the lock, compare recorded expected and observed pointers/files/host versions, complete matching steps and recheck readiness. A third-party edit is reported and retained. Reinstall/repair uses the packaged executable if the launcher has been removed. |
| Failed activation | Verify the preceding release and its exact store schema and host assets, restore the owned pointers and config, and restore the prior service state. Retire the verified failed candidate after recovery. Preserve committed user work. |
| Uninstall interrupted or owned config edited | Revoke owned access and remove journaled entries whose identity still matches. Preserve modified or unrelated entries and identify their paths. A retry with the launcher or release binary finishes remaining owned cleanup. An install finishes the interrupted uninstall under the same lock, keeping the data, then installs. |

For an intentional same-schema downgrade, provide an independently kept, verified bundle and invoke its `bin/reviewq install --from /absolute/previous-release`. Verify its manifest, exact database schema and managed host assets before activating it. For an interrupted install, retry the exact new bundle and arguments. The journal supplies the last verified step and the previous release path until the new service is ready.

Uninstall retains private settings, workflow data, backups, operator-authored reports and native histories unless `--delete-data` or the dashboard's "Also delete my data" asks to delete the owned data; native histories are never touched. Uninstalling the app does not stop a registered host conversation. Qualification covers a working reinstall and a rollback rehearsal in a disposable account.
