# Browser experience

A reviewer opens a team MR, reads its ticket and changes, talks to the registered lead while it works, and returns to the same passage after a reply. Queue, Runs and Notifications share the review drawer, selected run and delivery receipts. The service owns workflow classifications, provider reads, action outcomes and accepted reports. The browser owns navigation, presentation and unsent edits.

## Workspace

The sidebar shows the styled word Review followed by the Q glyph from `/icon.svg`, with **Agentic Code reviews** below. The same asset supplies the favicon and the collapsed mark. Review queue and Review runs sit below the brand, with Notifications and Settings at the bottom. Each navigation row has its own icon. The sidebar collapses through its seam handle.

The workspace header shows **Your workspace**, the view heading and **New review** for Queue and Runs. Queue lays out Board, Sprint, Repo, Ownership, Author, State, Hide, Sort and Clear in one compact wrapping strip, followed by the narrower search field. At full width the Review column shows ticket and MR identity, title, provider and next-action badges. Details shows the author or ticket assignee, initials, available update time and the open affordance. At narrower pane widths, Details stacks below the review body.

Opening an MR gives the review 53% of the desktop space beside the sidebar and the list 47%. Each pane scrolls independently. Drag the divider, use its arrow keys, or double-click to restore equal widths. Opening another MR restores the review default. At phone widths the navigation is horizontal and review detail takes the full available width with a visible return control. Closing restores the invoking row and its offset, including after keyboard navigation.

### Installing as an app and the stopped page

The dashboard is an installable web app with its own manifest and 192 and 512 pixel icons. **Settings → App → System** offers **Install app** when Chrome or Edge has offered installation, and otherwise says why it can't: already installed or not offered yet, running as the app, just installed, or a browser without the install offer. The app listens for the offer from its first script, since the browser fires it before Settings loads.

The app registers one service worker for the whole address at start. It handles notification clicks and page loads only: a page load that cannot reach ReviewQ shows the cached stopped page, and every API, asset and other request goes to the network. Where the browser supports static routes, API and asset requests never start the worker. Only the app writes the cache, storing a fresh copy of the stopped page each start.

The System page's **Quit** and **Uninstall** boxes, the uninstall screen and the stopped page show ReviewQ's name as the logo in the title, such as **Quit ReviewQ?**, and their explanations say "it" or "the app". While the tab holds unsent drafts, both boxes say how many will be lost. After the service accepts an uninstall, the app shows one centred card: **Uninstalling ReviewQ** with a turning ring while the service still answers a read made every 500 ms, then **ReviewQ is uninstalled** with a green tick once it stops answering. A service that still answers after 30 seconds was not stopped, so the page reloads and the app returns; the uninstall job's desktop notification says why. Only in the installed app window does the card say how to remove the app icon.

The stopped page says **ReviewQ isn't running** in the saved light or dark appearance, on the same card with a power mark. When served by the installed service it says monitoring, alerts and follow-ups are paused and offers **Start**, which asks the start port (dashboard port + 4) to start the service and repeats the request every 3 seconds, for up to 30 seconds, until the dashboard answers; it then opens it. Meanwhile the button reads **Starting…** and the mark turns into a ring. The repeat covers a request made just before a stop began, which systemd counts as already done. If it doesn't start, the page names `reviewq logs` with a Copy button. In the installed app window it also says how to remove the app if it was uninstalled: below the button, and in the notice when the start port was unreachable. A foreground or validation server shows no button and says to start the server again, then reload the page. The page keeps the default referrer policy, since the start port accepts only the dashboard's Origin.

### Opening and restoring a review

The app owns one confirmed selection. Use canonical links with a view (`queue`, `runs` or `notifications`), opaque `reviewId`, optional `runId` and drawer tab (`overview`, `agent`, `findings` or `changes`). Encode each parameter separately. Resolve the selection through `GET /api/v1/reviews/resolve?reviewId=…&runId=…`. Confirm the returned review ID, run ID and lead session key in one scoped lookup before enabling actions. A new MR defaults to Overview and its most recent registered lead when available. An explicitly requested but unavailable run produces a named unavailable view with a run picker. A new target clears the previous child and target-specific overlays. Child views present a breadcrumb to the lead and use their own native identity. A ticket-only row opens a ticket pane with its actual key.

Use ordinary browser Back/Forward for committed view, drawer and tab navigation. Search typing, splitter drags and live cursor changes do not fill navigation history. Preserve small per-tab preferences and bookmarks across reload, including list/filter choice, selected ticket, runs stage, archive filters, selected report receipt, disclosure/scroll anchor and panel width. A URL target wins over incidental saved state. Validate versioned preferences, tolerate disabled storage, and keep secrets, submitted text, pending actions and document bodies out of the URL and browser storage. Unsent drafts stay in memory across tab, child, MR and Settings navigation. Browser reload restores pending action status from durable service receipts.

**Unsent work across reviews.** The shell owns a memory-only draft store for lead messages, report comments/quotes, finding-disposition edits and native question answers, keyed to their actual target. Allow up to 128 occupied draft entries and 8 MiB total charged draft data across all views. Charge 256 bytes per entry plus two bytes per UTF-16 code unit in every retained key, text, quote, option and answer string. Count frozen in-flight values and newer edits separately when both exist. The protocol’s individual field and submission limits also apply. Keep one copy of shared immutable text. Remove empty/accepted drafts promptly, keeping edits made after the sent revision. A closed question with unsent text becomes a non-sendable draft that the author can copy or explicitly discard. Clear secrets on closure and signal that state to the author.

Before admitting a new draft, paste, attachment-free quote or edit, reserve its projected size. Evict clean entries first. If dirty or pending work occupies the count or byte cap, leave those entries intact, show a persistent **Draft storage full** status and offer a keyboard-accessible list of named targets with Copy, Open to send and Discard actions. Confirm explicit discard of a dirty entry. Allow text reduction and navigation/read-only work immediately. Never truncate a paste or completed IME edit to fit. Explain a rejected insertion beside its field and allow retry after space is available. Send stays an explicit action on the original confirmed target. Browser reload discloses that unsent drafts are memory-only.

### Reading, refreshing and acting

Keep the last confirmed same-target document in place during background reads. Show a centered, delayed 32px indicator only on an initial empty panel, expose its busy name immediately, reveal contextual text after three seconds, and use a static labeled state for reduced motion. Empty sources, filtered-out data, partial coverage, denied/missing sources, offline state and failure each need an appropriate message and recovery action. “No findings yet” requires a successful read. Reconnect silently after a brief transient failure when content remains current. Prolonged outage shows last confirmation time, relevant state and Retry. Put one warning for a shared connection failure at the far right of the workspace header above its actions. When a detail fills a narrow screen, reserve a slot immediately before its Close or Return control for the warning. Keep those controls in place as the warning appears or clears, and keep action failures beside their controls. A failed subview retains the shell, other tabs and drafts.

Use an accessible named region for each pane, heading order, native form controls, skip navigation and visible selected/expanded states. Tabs have labeled panels and arrow, Home/End and Tab keyboard behavior. Menus and dialogs close the innermost layer on Escape and return focus to its trigger. Keep the desktop drawer nonmodal so keyboard users can return to the queue. On narrow modal presentation the background becomes inert. Dynamic events never focus an incoming item. Announce actionable changes or failed submissions once in a small status region. Avoid placing the entire transcript in a live region. Check keyboard, touch, zoom, reduced motion, forced colors, wrapping and actual accessible names. [WAI-ARIA tab pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) · [WAI-ARIA dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

On each read capture the full resource key, selection generation and AbortSignal. Check the key again before committing the response, including after decoding and under rapid Back/Forward. A read of a new target cannot paint the preceding review’s contents or enable its Send button. The selected MR, pinned file revision, frozen report version, lead run and selected child have different lifetimes. Keep each independent. A submit captures the resolved target, version/receipt or exact native question, body and one submission ID. Apply the outcome to its captured owner after navigation. Keep entered text on failure. Reconcile uncertain outcomes against the service before offering another action.

## Documents and retained memory

The [review reader design](review-reader.md) governs range-rendered diffs, pane search, live and completed Markdown, and drawing retention.

| Resource | Ownership and release |
| --- | --- |
| Queue or Runs | Fetch summary pages and counts for the active view and query. Keep a bounded window plus small stable identity/offset bookmarks. A card has no transcript, stored report Markdown, raw patch, ticket comment history or provider object. |
| File | Fetch revision-bound file pages and discussion metadata independently. Stream the actual patches in provider order through one scroll pane. Resolve picker jumps to a verified file page, including paths beyond the current page. Retain up to five file metadata pages and keep nearby bodies within eight patches and 4 MiB of admitted UTF-8 source. Prioritize the viewport and scroll direction. Release distant bodies, portal roots and requests. Native code and its selection survive same-revision discussion updates. Keep one compact reading bookmark per review. |
| Thread | Anchor by provider, MR, complete diff revision, side, path and old/new line. Use stable thread and note IDs. Earlier-revision and unmatched positions retain original coordinates and a source link. A change above a reader compensates their saved anchor offset once. A change below must leave it fixed. |
| Transcript | One active run/native session/generation, one outer measured viewport and six page descriptors at most. Account for retained strings, metadata, previews and concurrent decoded reads under the 8 MiB browser history budget. Evict distant content first and retain cursors to fetch it again. Use four 64 KiB ranges per expanded body at most. Preserve only compact anchors for inactive sessions and close scoped subscriptions. |
| Report | Bind the displayed version to the accepted receipt/hash and read its size metadata first. Parse only an admitted rich document. Measure visible semantic sections with the outer scroller and preserve section jumps and indivisible table rows, code fences and disclosures. Release the active source, tree, diagrams and parser work on exit. Above the rich envelope, read the exact immutable source in bounded ranges. |
| Rich content | Parse GFM and sanitize allowed markup before creating React nodes. Preserve defined links, source locations, fenced code, tasks, tables, nested lists and authored disclosures. Render remote images as labeled links. Lazy-load strict Mermaid for an actual diagram, support pan/zoom/Fit and expose its source on render error. No runtime CDN or automatic attachment loads. |

### Search in Changes

Typing part of a filename, abbreviated filename letters or a literal code fragment updates suggestions without moving the reader. Use the revision-bound path catalog for filenames. Find code literals regardless of letter case, preserving the source spelling in each highlighted result. Search the available diff hunks, including context, additions and removals. Group matching snippets by file, mark the matching text and identify its side and line. Show results progressively and distinguish a completed search with no matches from one still reading GitLab or limited by the provider. Arrow keys choose a result. Enter, a click or a tap loads its destination window and highlights the exact occurrence. Escape returns focus to the picker button. When a head or query changes, discard obsolete results and pending jumps. Chrome needs only a bounded result page and the destination window for this interaction.

A jump belongs to one review, its exact GitLab diff revision and a verified file ID. Use the old side for deletions and the new side for additions and shared context. Lines are one-based. For a code match, `hunk` is the UTF-8 byte offset of its hunk header. `sourceStart` and `sourceEnd` are the half-open byte range of the matched text in the original unified patch, counting row prefixes and original line endings. `highlightStart` and `highlightEnd` are UTF-16 offsets into the returned snippet, suitable for JavaScript string slicing. For example, in a deleted line containing the same word twice after an emoji, choosing the second result highlights only the second occurrence on the old side. A new wheel, touch, keyboard or scrollbar navigation cancels a pending jump. Keep the current code visible while the destination loads.

The closed button shows the basename, current file position (for example, “3 of 12”) and trailing caret on one line. Align the caret vertically with the filename. Show folder context in the open picker and the full path on hover. Place a single Filters button beside the Changes views. It shows the active filter count and opens the participant and resolution choices together. Applying or resetting a choice preserves the file query.

### Full document and bounded source modes

The following initial limits apply before fetching a body for rich rendering. A physical line includes ordinary code, hunk headers and metadata. Count bytes in the original UTF-8, count an unterminated final line, and exclude LF or CRLF terminators from the longest-line measurement. Each limit is inclusive. Missing trustworthy size information selects bounded range retrieval.

| Loaded resource | Full rich mode | When a limit is exceeded |
| --- | --- | --- |
| Complete patch | Up to 2 MiB source, 20,000 physical rows and 16 KiB per physical line. Keep compact, stable native text for Find and copy through the last line. Mount rich rows and decorations around the viewport with a small lookahead and pin active selections, focus and expanded threads. | Use the same rich patch renderer over revision-bound source windows, keeping threads beneath their verified lines. Bound row and byte reads, support long-line continuation, range copy and pane Find. Retain direct source access, download, coverage and provider link. |
| Accepted report | Up to 1 MiB source, 10,000 physical lines and 16 KiB per line. Apply a 60,000-node and 128-level depth ceiling to the rich document tree. Parse at most one active report, isolating/cancelling costly parse work on replacement. Admit only bounded validated output to the main thread. | Show **Large report · source view** or a precise formatting-limit reason. Read a single source page of up to 12,000 Unicode scalar values, identify the receipt/hash, and offer Start, Previous, Next, End and Download Markdown. The page contains original text and offsets, including Markdown the formatted view cannot represent. |
| Markdown and diagrams | The same document/line/tree limits apply to rich Markdown inputs. Use Mermaid strict mode without external resources. Accept up to 30,000 source characters and 500 edges for a diagram. Only render diagrams in mounted content. | Render a labeled source disclosure or bounded plain-text excerpt. Never send an oversized figure to Mermaid. Discard stale parse/layout results and retain the underlying source link or continuation. |

The 12,000-addition worked patch has 409,799 bytes and 12,001 physical rows including its hunk header. It opens in full native mode. For a windowed large patch native Find covers mounted text and Changes Find covers the entire available revision. Label partial provider coverage. An explicitly opened raw excerpt exposes its displayed range. A suffix range or final report offset reaches the final text without visiting intervening pages. A giant physical line spans consecutive ranges, with continuation labels and exact copyable Unicode. An incomplete provider patch exposes its retrieval limit and provider link. Offer a complete download only when complete bytes are available. For a complete source, download through an authenticated, revision/receipt-bound streaming attachment. The browser never materializes that download as an application Blob or hidden formatted document. Download/original-source access remains available to a reviewer who needs whole-document fidelity. Hash-bound report feedback can quote an exact source range in either rendering mode. [Worked patch bytes](../plans/01-foundation/fixtures.md#source-material) · [Review workflow](review-workflow.md)

**Active selections at a memory limit.** While text is selected, pin the mounted native entries and all body ranges from the selection start through its end, along with the row holding keyboard focus. The history window reserves the maximum decoded charge and a page/range slot before issuing a read. Reclaim the farthest unpinned ranges/pages first. If the visible selection spans all six pages, a seventh page stays unread. If all four body ranges are selected, a fifth stays unread. Apply the same rule when the byte budget fills earlier. Keep one pending invalidation or newer cursor, leave the selection and its text intact and show **New messages available** or **More output available** with Copy selection, Clear selection and a labeled navigation action. Background refresh cannot clear it. After explicit clear or Jump to latest, release pins and catch up from the service in bounded pages. A focused form remains mounted independently of automatic refresh.

Use the browser’s native Find and cross-line selection throughout an ordinary loaded file, including its last line. Jump to other files from the persistent file picker. Keep the line number gutters out of clipboard text and preserve tabs, whitespace, Unicode and mixed-line order. A new file revision can be offered explicitly while text is selected or the reviewer is composing. Preserve the old revision label until replacement. Giant, binary, truncated, unavailable and renamed files must describe their actual coverage. If only part of a diff is available, the UI states the limit with the original source link. Keep native code text searchable as the browser skips offscreen layout. ## Populated acceptance

Use one seeded scenario to visit the normal path, e.g. two projects with the same MR IID, two leads on one MR, one child, a Jira-only ticket, one accepted report with Mermaid and a quoted finding, a mixed diff with inline/general/earlier threads, an actionable question and separate notification IDs. Generate long history and 1,200/12,000-line diff variants from a tiny recipe. Switch repeatedly, retain a selection while comments change, disconnect after Send, return to the original run and reconcile the same receipt. Compare the actual populated desktop, narrow split and phone screenshots. Verify keyboard/screen-reader order and touch interactions on the rendered product. Inspect a physical trackpad at its real refresh rate for scrolling regressions.

Use the [browser budget checks](acceptance.md#browser-budgets) for measurement definitions, workloads and acceptance thresholds. Keep new permanent tests for concrete regressions within the repository-wide 500-case cap.
