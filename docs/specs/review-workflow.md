# Review decisions, findings and selected-thread checks

A reviewer can privately investigate an MR, hand off exact findings, ask the registered lead to act, and verify what reached GitLab. A local decision, a saved report, a native delivery, a confirmed GitLab action and an MR merge each have their own evidence. All examples use the selected installation and its configured GitLab origin, project ID and MR IID. The implementation owners are [ACTION](../plans/04-workflow/actions.md), [REPORT](../plans/04-workflow/reports.md) and [FOLLOW](../plans/04-workflow/followups.md).

## What the reviewer sees

| Operation | Observable outcome |
|---|---|
| Track, register and prepare | Tracking one MR adds it to discovery exceptions. Registering an actual native lead adds a run under that MR. Preview shows target checkout, skill or custom prompt, model, effort and revision. Only Start invokes the native host. A registration or accepted native send alone leaves reviewed revision unknown. [Sessions](agent-sessions.md) |
| Prepare several reviews | Queue and Runs share Select MRs. Select only open MRs in scope. Drop selections outside the effective scope. Before submitting, show the exact targets. Intersect available catalog/model/effort choices and expand `{ticket}` in each target's repository context. Launch each through HOST's normal single-target preview/start. Retain one submission ID and visible result per MR. On rejection or lost confirmation continue independently, retain the outcome and permit inspection. Closing the panel leaves started reviews running. No durable job exists for targets the operator never submitted. |
| Save a local decision | Review complete, Waiting on author or Clear local review record goes through QUEUE's SHA-checked decision command. Follow-up handled records only the observed GitLab event and per-session response/attention checkpoint. Later arrivals stay pending. Notification read/dismiss touches only named occurrence receipts. Selecting a report, recording a nonblocking finding or clearing a decision does not publish anything. [Queue and Settings](queue-and-settings.md) |
| Declare comments, approval or both | The registered lead binds the current actual user request, exact open MR revision and intended comment hashes. After native execution, ReviewQ independently reads GitLab. A comments-only confirmation hands work to the author even for an approve verdict. For explicit approval, read back the authenticated user's own approval. |
| Deliver findings or ask a question | A lead helper receives a handoff acknowledgement. Findings presents the accepted report with its reviewed SHA, content hash and receipt. While waiting, keep the previous version readable. A bound question can require input without creating a report. A failed replacement shows its own reason. |
| Reply to a report | Feedback captures the displayed immutable version and exact optional source quote. The dispatch receipt names its lead and report even if another version arrives or the drawer changes. Preserve the draft on error. |
| Monitor or check selected threads | Manage monitored threads selects an assigned lead and original published reviewer notes, including an explicit empty selection. Enable, pause, resume and Review selected updates now act on that MR. A private check can draft a reply. Only a later explicit user request can authorize publication. |

The resulting stage, focus session and reason drive Queue, Runs, browser totals and MCP from one read snapshot. One card represents each MR with at least one registered lead. Pick the newest registered lead by start time and a stable key, follow real parent links for its current family, and retain all earlier runs in the drawer. QUEUE owns `classify_review(&WorkspaceEvidence) -> ReviewStageView` in `crates/domain/src/review_stage.rs`. Inputs include MR state/head and handed-off time, the observed checkpoint, all registered session statuses and native input/attention times, report delivery/semantic receipt, current action, recovery and monitor evidence. Return stage, reason kind, target lead and focus, `hasAgentQuestions`, coverage and independently observed approval. Bare timestamps and UI filters cannot manufacture execution.

Apply the following precedence, first match wins.

1. Closed or merged goes to Archived. Missing MR evidence for an existing registered run needs input. Keep unavailable distinct from closed.
2. Relevant blocking questions or permissions need input immediately. Check actual native question state from the newest review start or a later active personal approval. A newer question in an explicitly resumed older session can qualify. An optional unanswered question remains visible as `hasAgentQuestions` while the current lead works. A working current lead shows Working. A current unhandled family failure or unavailable state needs input unless superseded by a later lead report or handled recovery. Otherwise another working registered member makes the MR Working. Any remaining current question needs input.
3. Active action verification is Working. With idle native work, a failed findings delivery needs input and an in-progress capture is Working. A pending action retry waits and an uncertain continuation needs input. For a qualifying Codex quota, model-capacity or access interruption, eligible automatic recovery waits and disabled/cancelled recovery needs input. Verified final findings for that exact interrupted turn end its recovery eligibility. Keep the last observed state and show freshness separately when a provider read is delayed.
4. Withdrawn personal approval can need a decision. For an unapproved MR, an accumulating or reserved automatic check waits. A selected reply, edit, reopen or unresolved handling of an actual resolution after the checkpoint needs input. Code-only changes remain visible in coverage/notifications. A completed focused result with a new requested decision needs input until handed off or handled. Track outstanding actions across batches even if a later batch says waiting on author. Queued work takes precedence over an older unread result.
5. A current verified comments-only action waits on author. A current confirmed approval waits on merge. Completed action evidence is scoped to revision and semantic report identity. An unhandled new full report, evidence correction or newly started review can need input. Otherwise use the latest valid local/GitLab handoff for Waiting on author or Awaiting merge. An open, finished lead lacking a handoff needs a decision. An active configured-reviewer approval suppresses routine reply/commit prompts while preserving their inbox events. The MCP filters `waiting_on_us` and `awaiting_input` select `needs_input`. `agent_questions` selects the independent question flag.

## Commands, reads and authority

Paths below are under `/api/v1`. The shared envelope wraps each data shape in `{data,cursor}`. Lists use `items,nextCursor` and stable opaque scope-bound page cursors. IDs are opaque strings, revisions decimal strings, Git SHAs full hashes, timestamps UTC. `submissionId` on a user mutation is a stable caller-generated ID scoped to operation, actor and exact target. Identical replay returns the stored result before evaluating a now-stale precondition. A different payload for that identity conflicts. Native tool calls use their proven provider/session/turn/call identity for the same purpose. HTTP adapters verify browser/native grants, method, scope, strict shapes and body caps. ENTRY delegates its CLI and MCP commands to the same app services. The browser cannot assert a native tool identity or accepted GitLab result.

Use the [shared error contract](data-contracts.md). Malformed declarations return invalid_request. Wrong grants map to unauthorized/forbidden, inaccessible or absent targets to not_found, altered replay to idempotency_conflict and obsolete expected state to stale_revision. Use conflict for an applicable workflow whose proven binding or evidence no longer permits the transition. Use precondition_failed for an immutable content If-Match mismatch. Use payload_too_large for a metadata/rich-view byte budget, range_not_satisfiable for an invalid range, and unavailable for temporarily unreadable proof. Use the common structured error envelope and stable codes. Persist operational failure, retry and unknown delivery states even if a request disconnects. A read does not consume review work. HTTP status communicates admission or retrieval. Durable receipts supply evidence of later transitions.

Use typed application failures so callers choose a recovery action from the cause. `TargetMismatch` carries which authority boundary failed (review, lead, turn or call). `PreconditionChanged` carries the changed field and currently observed revision (head, disposition, monitor, report identity or native position). `IdempotencyConflict` identifies a reused ID with changed content. `EvidenceUnavailable` names the source and whether a fresh read is possible. `InvalidEvidence` indicates source hash, quote, completeness or scoped finding validation. `DeliveryUncertain` carries the existing submission ID for status lookup. The transport maps these to the common codes and sanitized messages. Unknown delivery after admission is a durable receipt the user can inspect. Compare-and-set failures keep the draft and return enough scoped identity for a fresh read.

## Verified actions and dispatch

A native declaration needs a currently working registered lead, matching provider native ID, run, review, turn, active call and **latest complete actual user input**. Match a known user submission to its persisted purpose. Reject an automatic/child prompt, hidden instruction, older entry, pending newer manual send or mismatched Claude companion entry. Re-read the native entry and current open MR after any async evidence read. For a cancel, verify the superseding user input. `comments` and `both` need 1–50 distinct exact UTF-8 SHA-256 body hashes and a discussionId for replies. `approval` and `cancel` carry zero comments. The native lead performs only the authorized remote work. A scoped automatic prompt may never declare new authority.

Drive `working → checking → completed | working | retry_wait | needs_input | cancelled`. Compare each note against the authenticated GitLab user's ID, requested digest, optional discussion and positioned head SHA. Store confirmed note IDs/time. Read approval for that exact authenticated user, independently of other configured reviewer identities or aggregate approval count. Conclusive absence requires complete current evidence. Keep unknown on partial reads, preserve prior confirmations, and show remaining targets. Keep original request identity, currently queued retry and last executed retry distinct. On superseding input, stop, closure or changed head, cancel only this authority and its known-unstarted continuation. An already sent operation can require readback. Another user's approval cannot complete ours.

Use the single HOST dispatcher. In one store transaction, save the action/retry and its exact outbox row, then wake HOST after commit. At claim and immediately before native submission, recheck current input/turn, permission, original SHA, live approval/notes, owner, capability, known completion and pending user work. A fresh read that already confirms the targets completes the action without sending. Continue only genuinely absent targets. At most three automatic sends for the same explicit request, a 10 s base wait and capped doubling for unknown evidence through 80 s. Hold and re-read unknown GitLab outcomes. An uncertain native send enters needs_input and is reconciled by exact submission ID. Inspect halted, uncancelled actions about once a minute so later confirmed success can close them. No automatic action continuation may steer a working turn. The native provider's final cross-client race remains visible through native receipts.

## Report acceptance and continuity

The accepted artifact belongs to the exact registered lead. Native tools stage one of the following handoffs. Metadata including bound follow-up coverage fits 128 KiB, allow 16 KiB HTTP overhead for routing. Keep file/response Markdown outside that limit. A native file payload specifies a canonical absolute path and SHA-256. Codex hashes the bytes before submission. Authenticated Claude can request server-side hashing for its actual file call. Restrict file access to the proven native execution and its authorized report source. Read one regular file descriptor, hash its raw bytes, decode valid UTF-8 without normalizing BOM, CRLF or trailing newline, check for replacement/mutation and verify again at capture. Response capture reads all chunks of the exact visible final result from a normally completed matching turn. Terminal output, ordinary replies, child results and text that resembles a receipt carry no report authority.

| Handoff | Acceptance |
|---|---|
| `final{source,revision,verdict,…}` | Revision is an exact full SHA or `{sha:null,reason}`. Verdict is approve/request_changes/blocked/not_specified. Verify canonical completed successful native tool call, proven origin/generation/turn/call/position and receipt marker for the declaration. A final file can be accepted after a later turn failure when that exact tool succeeded with matching bytes. A response needs normal completion plus the full canonical result. Append immutable Markdown and advance current per-run receipt. Normal complete coverage records declared source and available target separately. |
| `unchanged{accepted:{receiptId,sha256},source,…}` | Require the current accepted identity and original source. Re-hash an accepted file. Require normal matching turn completion and successful native tool proof. Record the outcome and optional batch assessments against that accepted version. Preserve its report bytes, full-MR SHA and version count. |
| `needs_input{reason,…}` | Record actual reason, exact native turn and proof. Complete no finding assessment by implication. Keep prior accepted report and the open follow-up binding so a verified resumed turn can finish it. |

The legacy Codex marker includes the receipt hash and canonical declaration hash in native tool output. Derive the receipt with SHA-256 of compact UTF-8 JSON `[provider,nativeId,turnId,callId]`. Hash the validated declaration in its defined field order including server-bound scope. For the native compatibility hash, serialize compact UTF-8 JSON with the schema's ordered keys, JSON string escaping, omitted absent optional fields and no ASCII escaping of printable Unicode. Preserve array order. For final use outcome, source, revision, verdict, amendsReport, correctsReport, coverage, changes, sectionChanges, assessments, reconcilesReceiptId in that order. For unchanged use outcome, accepted, source then the same applicable completion fields. For needs_input use outcome, reason and its completion fields. File source keys are kind, path, sha256. Response source is just kind. Revision starts with sha then reason when unknown. Preserve imported declarations and their original digests. Verify the original tool invocation, completion and matching marker. A marker printed by a different command cannot complete the handoff. Same call/payload returns the same receipt. Same call with a different declaration conflicts. Prevent an older source position from overtaking a newer accepted handoff, including after history rotation. A declaration can be staged while Codex history flushes but cannot be accepted on that basis. At terminal readback compare accepted receipt, content hash, reviewed SHA/reason and provenance to the intended output.

### Worked native receipt

Use a file whose complete UTF-8 text is the JSON string literal `"# Review\n\nCafé verified.\n"` decoded once. Its 26 raw bytes include a final LF. The native fixture uses provider `codex`, native ID `fixture-native-41`, turn `turn-7` and call `call-3`. Its receipt is SHA-256 of `["codex","fixture-native-41","turn-7","call-3"]` encoded as UTF-8. The following one-line compact declaration has no whitespace outside its string values.

```json
{"outcome":"final","source":{"kind":"file","path":"/tmp/rq/report.md","sha256":"72294d53004f3b01477bc9d6195fe32fefeab460ad3289eb164277fb8774d4d7"},"revision":{"sha":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"},"verdict":"not_specified"}
```

Exclude the code block's line terminator from the declaration hash. The original native tool must return this exact proof line (a recorded replay can substitute `recorded`).

```text
ReviewQ report pending_completion; receipt abc099a917052885ba457d3e0f9776a930bf514874b81f4d1d09582762b38763; declaration ee6282409951623946f1d1abc922cb9421e1e161e9049b270f48a58e5f506cb5.
```

The receipt and declaration hash authenticate no caller by themselves. Bind the matched marker to the original native result, then check the accepted content hash and reviewed revision independently. Reusing the digest values with a different actual test path requires recalculating the declaration hash.

## Capturing and revising accepted findings

Pin base accepted receipt/hash and user disposition version at handoff. Capture report bytes, parse evidence and obtain native/refresh proofs outside SQLite. One conditional transaction checks those pins, native proof order, current handoff, run membership and frozen batch if present. It appends the version, CAS-advances the current pointer, saves outcomes and semantic attention identity, updates covered observations and inserts the due notification together. On conflict retain the captured unaccepted bytes, hash, reason, provenance and exact targets for reconciliation. Preserve the last accepted pointer and user decisions. Use a distinct short failure transaction. Reopen pending records on startup, reconcile by call identity, and publish invalidations/wake dispatch after commit. At most one correction request per active native turn, durably reserved before asking the same turn to correct missing/invalid metadata. Historical reconciliation is read-only against the host.

A report can declare a full review, a private scoped check, or a change to an existing accepted report.

| Form | Required continuity |
|---|---|
| Full review | Establish a new complete-MR baseline at the declared reviewed SHA, or retain the unknown reason. Display authored findings, counts, severity, proof limits and verdict. Registration's requested SHA, current head, Markdown recommendation and GitLab approval are independent facts. |
| Selected-thread final/unchanged | Bind to FOLLOW's exact batch, frozen submission, monitor generation, current or proven descendant native turn, baseline receipt/hash, disposition revision, checked source/target, every observation ID/version and lineage. One assessment per distinct selected discussion. Unselected outstanding cards retain exact evidence and disposition. Preserve standalone questions, unknown sections and material qualifications. Terminal outcomes fixed, clarified_withdrawn or superseded may retire cards with explicit evidence. Partly_addressed, still_present and unverified retain current cards. Use the cumulative ancestry, including newly added findings from earlier scoped batches. Only a full review can advance fullMrReviewedSha. |
| `amendsReport:{receiptId,sha256}` | Publication/disposition edit on the exact current report. Reuse its reviewed SHA, coverage, finding identities, questions, dispositions, conclusions and attentionReceiptId. Refresh GitLab outside the write transaction before capture. Append a version without another ready alert or completing an old batch. |
| `correctsReport:{receiptId,sha256,kind,reason,findingIds,evidence}` | Retain reviewed revision and coverage. Evidence references exact accepted finding ID or section title and digest. Presentation may promote exact existing evidence to a card and retains verdict, body and semantic attention. Evidence correction requires a declared change per affected ID and creates new attention. Preserve unselected evidence and user decisions. A correction that cites old evidence cannot assert fresh investigation. |

Recognize authored level-three F-number headings and explicit metadata on parsed Markdown blocks. Quoted or fenced words cannot change blocking. A scoped change describes findingId, conclusion, reason, checkedSha and selected discussion IDs. A changed standalone section additionally names exact baseline title/hash and replacement title (null only for an explicit terminal outcome). Each assessment supplies discussionId, conclusion, reason, findingIds and nextAction `review` or `waiting_author`. Missing historical nextAction remains actionable. Enforce exact scope, complete unique assessments and stable identities. A user-recorded nonblocking finding cannot silently become blocking. Preserve immutable old acceptance and user overrides separately. Feedback locates the exact selected bytes/quote, including an older accepted version and Unicode. Both the rich Findings reader and the bounded source reader can supply quotes. Match the submitted quote exactly at the specified scalar offset and length against the named immutable version. A repeated literal quote requires its reference to identify a particular occurrence. Never manufacture a source range from synthetic headings, decorated labels or rendered HTML. The report viewing checkpoint, decision checkpoint, batch assessment viewing checkpoint and notification receipts advance independently.

### Reading large reports

Compute byteLength in UTF-8, totalCodePoints in Unicode scalars, and physical line statistics when capturing an artifact, then persist with its receipt. Count LF boundaries (consume CRLF as one delimiter), exclude line terminators from maxLineBytes and do not count a trailing empty line after terminal LF. An empty artifact has zero lines. An imported report with missing size fields must obtain these stats by streaming its stored bytes before permitting a rich read. Return metadata first. Serve `view=markdown` only when byteLength ≤1 MiB, lineCount ≤10,000 and maxLineBytes ≤16 KiB. An over-budget explicit rich request returns payload_too_large with zero Markdown bytes. The summary already provides the metadata and immutable identity needed for section and download routes. Report acceptance still retains every verified byte.

For larger files, or on rich parser/AST-budget exhaustion, open a paged plain Markdown source reader pinned to the accepted version. Use at most 12,000 code points per page, choose `max(0,totalCodePoints-12000)` for Last, and provide previous, next and explicit offset navigation. Quote feedback can refer to global source offsets spanning visible source text. STORE supplies immutable chunks up to 64 KiB and indexed source offsets. End each short read snapshot before waiting on the network. Offer the complete original as a streamed native download without buffering the entire artifact into a JavaScript Blob or retaining it in browser cache. Keep summaries and notification invalidations free of report bodies.

## Selected-thread scheduling

Global default off, per-MR enabled/disabled overrides win. Monitor states are enabled, paused and archived. A complete authorized current MR read and stable reviewer identities are prerequisites. Choose latest accepted report's lead, or the sole registered lead when no report exists. Multiple possible leads without reports require a selection. Preserve assignment across navigation and new reports. Initial enrollment uses actual published notes by the configured reviewer identities. Exclusions follow original note IDs if GitLab promotes an individual comment into a discussion. Require a unique identity match. A matching filename, similar body, resolved badge or private finding cannot establish a thread.

| Event or decision | Recorded work |
|---|---|
| Initial full snapshot or new enrollment | Store baseline of note IDs/actors/body hashes and resolution. Adopt only eligible outstanding QUEUE events on selected discussions after the handled boundary, recording adoption with the observation in the same transaction. An already resolved thread starts resolved. If a new review note and subsequent external reply first appear together in a later complete sync, enroll the note and capture its reply once. |
| Reply, edited external body, resolution or reopen | Compare exact selected discussion and known original IDs on a complete snapshot. Record observation ID, discussion version/fingerprint, action kinds, actors where known, note and finding IDs. Exclude own identified actions, system notes and timestamp-only changes. Incomplete reads or ambiguous/missing originals cannot supply negative evidence. Commit-only changes, unrelated feedback and old read/dismiss history never schedule by themselves. Polling cannot reconstruct an event wholly between two snapshots. |
| Configure, pause, resume, review-now | Observe retained selections before editing. Advance generation for a meaningful edit. Carry remaining unstarted observations into the new generation, retain exclusions, and validate every selected reviewer note. Pause holds known pending work. Resume requires fresh MR and approval state. Manual Check Now admits all selected available concerns at their observed versions immediately, even with no new reply. An unavailable selected thread or empty selection returns a named reason. Bulk configure/pause uses a per-target preview and exact per-target commands, reporting skipped/failed targets separately. |
| Approval, closure or loss of identity | A confirmed approval by a configured monitored reviewer pauses automatic work. Unrelated approvals have no effect. Unknown approval holds. Preserve pending/uncertain delivery for exact reconciliation, cancel proven-unstarted ineligible work. Already executing private work may deliver its frozen result. Merge/close archives the monitor, reopening requires explicit resume. A changed reviewer identity requires revalidation. |
| Due work | Set due time to min(last observation + 60 s, first + 180 s). Run a coalesced due pass at startup, after relevant commits and about every 10 s. One active/reserved attempt per MR. Respect the 1–8 global active cap, default 2. Distinguish active native execution/reservation from a confirmed idle question-held or ended run. Retain exact binding for a later answer even when freeing its global slot. Unknown provider state, uncertain submission and unfinished proof still reserve capacity. |
| Freeze and deliver | Fetch fresh MR and recheck saved Settings revision, open/unapproved state, monitor, recipient, actual thread availability and HOST eligibility. Freeze bounded groups (start with 10 observations, maximum 12,000-character prompt, carry unsent remainder). Commit exact members, checked head, target SHA if actually known, parent/disposition version, submission ID, private prompt and outbox together. Wake HOST after commit. A reservation is pending. Only an exact accepted native turn changes its state to executing. A new event after freeze goes to a successor. |
| Finish, stop, recover | Complete only the exact executing batch after REPORT proves its matching handoff. Needs-input holds its scope and claims zero completed assessments. Unknown send stays owned while exact native history is inspected. If a known-unstarted submission is rejected release it and requeue only still-eligible members. Explicit stop pauses monitoring. An ended attempt with retained conflicting evidence can be reconciled by a successor carrying the original observations and lineage. Retire the retained candidate only once accepted groups cover every original observation ID, version and discussion. An unrelated manual turn never consumes a batch. |

For example, suppose a monitor links original note 91 in discussion D7 to finding F-01. A reply creates observation O4 at discussion version 3. The accepted baseline also contains F-02 under an explicit nonblocking disposition. A native check with no Markdown changes can send the following semantic assessment against its current accepted report.

```json
{"assessments":[{"discussionId":"D7","conclusion":"still_present","reason":"The selected guard still permits an empty list. The original note already asks for that guard.","findingIds":["F-01"],"nextAction":"waiting_author"}]}
```

The server binds O4/version 3 and the checked source SHA from the frozen batch. The user helper never supplies an invented observation or turn. That result adds one completed batch and zero report versions. F-02 remains an outstanding card with its earlier checked revision and disposition. A later reply creating O5 remains eligible even if it arrives before the first result is viewed.

Every automatic delivery checks pending questions/permissions, busy related sessions, earlier pending handoff, manual send/unknown receipt, provider readiness, preserved native model/effort and current eligibility at claim and send. Native model/permission recovery uses HOST's same outbox and only legal capacity evidence. It can extend an existing batch to the exact acknowledged resumed turn or an unambiguous same-session Codex root turn in the original executing lineage. A prior permission to publish never broadens a private check. Threads are evidence. The prompt authorizes reading and drafting only. Closing the drawer, viewing a result or losing the HTTP response cannot reauthorize a send.

## Verification

Use the fixture publisher and controlled host adapter first. For live dispatch exercise the ordinary foreground service with synthetic provider sources, a task-owned signed-in native host and a disposable profile as in SLICE. Validation mode disables sends and serves read-only inspection. Acceptance FIND-1, SEND-1 and WORK-1 name the shared readbacks. The [ACTION](../plans/04-workflow/actions.md#evidence), [REPORT](../plans/04-workflow/reports.md#evidence) and [FOLLOW](../plans/04-workflow/followups.md#evidence) briefs supply the exact positive postconditions, collision cases and evidence owners. Compare persisted receipt/ID, accepted source digest, revision and provider-native occurrence. A green simulated host alone establishes fixture behavior only. [Acceptance](acceptance.md)
