# Review decisions, findings and selected-thread checks

A reviewer can privately investigate an MR, hand off exact findings, ask the registered lead to act, and verify what reached GitLab. A local decision, a saved report, a native delivery, a confirmed GitLab action and an MR merge each have their own evidence. All examples use the selected installation and its configured GitLab origin, project ID and MR IID. The implementation owners are [ACTION](../plans/04-workflow/actions.md), [REPORT](../plans/04-workflow/reports.md) and [FOLLOW](../plans/04-workflow/followups.md).

Preview shows target checkout, skill or custom prompt, model, effort and revision. Only Start invokes the native host. A registration or accepted native send alone leaves reviewed revision unknown. [Sessions](agent-sessions.md) |
| Prepare several reviews | Queue and Runs share Select MRs. Select only open MRs in scope. Drop selections outside the effective scope. Before submitting, show the exact targets. Intersect available catalog/model/effort choices and expand `{ticket}` in each target's repository context. Launch each through HOST's normal single-target preview/start. Retain one submission ID and visible result per MR. On rejection or lost confirmation continue independently, retain the outcome and permit inspection. Closing the panel leaves started reviews running. No durable job exists for targets the operator never submitted. |
| Save a local decision | Review complete, Waiting on author or Clear local review record goes through QUEUE's SHA-checked decision command. Follow-up handled covers the displayed GitLab events, report and session attention, and exact completed follow-up batches. Later arrivals stay pending. Notification read/dismiss touches only named occurrence receipts. Selecting a report, recording a nonblocking finding or clearing a decision does not publish anything. [Queue and Settings](queue-and-settings.md) |
| Declare comments, approval or both | The registered lead binds the current actual user request, exact open MR revision and intended comment hashes. After native execution, ReviewQ independently reads GitLab. A comments-only confirmation hands work to the author even for an approve verdict. For explicit approval, read back the authenticated user's own approval. |
| Deliver findings or ask a question | A lead helper receives a handoff acknowledgement. Findings presents the accepted report with its reviewed SHA, content hash and receipt. While waiting, keep the previous version readable. A bound question can require input without creating a report. A failed replacement shows its own reason. |
| Reply to a report | Feedback captures the displayed immutable version and exact optional source quote. The dispatch receipt names its lead and report even if another version arrives or the drawer changes. Preserve the draft on error. |

Enable, pause, resume and Review selected updates now act on that MR. A private check can draft a reply. Only a later explicit user request can authorize publication. |

The resulting stage, focus session and reason drive Queue, Runs, browser totals and MCP from one read snapshot. One card represents each MR with at least one registered lead. Pick the newest registered lead by start time and a stable key, follow real parent links for its current family, and retain all earlier runs in the drawer. QUEUE owns `classify_review(&WorkspaceEvidence) -> ReviewStageView` in `crates/reviewq-domain/src/review_stage.rs`. Inputs include MR state/head and handed-off time, the observed checkpoint, all registered session statuses and native input/attention times, report delivery/semantic receipt, current action, recovery and monitor evidence. Return stage, reason kind, target lead and focus, `hasAgentQuestions`, coverage and independently observed approval. Bare timestamps and UI filters cannot manufacture execution.

Apply the following precedence, first match wins.

1. Closed or merged goes to Archived. Missing MR evidence for an existing registered run needs input. Keep unavailable distinct from closed.
2. Relevant blocking questions or permissions need input immediately. Check actual native question state from the newest review start or a later active personal approval. A newer question in an explicitly resumed older session can qualify. An optional unanswered question remains visible as `hasAgentQuestions` while the current lead works. A working current lead shows Working. A current unhandled family failure or unavailable state needs input unless superseded by a later lead report or handled recovery. Otherwise another working registered member makes the MR Working. Any remaining current question needs input.
3. Active action verification is Working. With idle native work, a failed findings delivery needs input and an in-progress capture is Working. A pending action retry waits and an uncertain continuation needs input. For a qualifying Codex quota, model-capacity or access interruption, eligible automatic recovery waits and disabled/cancelled recovery needs input. Verified final findings for that exact interrupted turn end its recovery eligibility. Keep the last observed state and show freshness separately when a provider read is delayed.
4. Withdrawn personal approval can need a decision. For an unapproved MR, an accumulating or reserved automatic check waits. A selected reply, edit, reopen or unresolved handling of an actual resolution after the checkpoint needs input. Code-only changes remain visible in coverage/notifications. A completed focused result with a new requested decision needs input until handed off or handled. Track outstanding actions across batches even if a later batch says waiting on author. Queued work takes precedence over an older unread result.
5. A current verified comments-only action waits on author. A current confirmed approval waits on merge. Completed action evidence is scoped to revision and semantic report identity. An unhandled new report or newly started review can need input. Otherwise use the latest valid local/GitLab handoff for Waiting on author or Awaiting merge. An open, finished lead lacking a handoff needs a decision. An active configured-reviewer approval suppresses routine reply/commit prompts while preserving their inbox events. The MCP filter `needs_input` selects the dashboard's Awaiting input stage. `agent_questions` selects the independent question flag.

## Commands, reads and authority

Paths below are under `/api/v1`. The shared envelope wraps each data shape in `{data,cursor}`. Lists use `items,nextCursor` and stable opaque scope-bound page cursors. IDs are opaque strings, revisions decimal strings, Git SHAs full hashes, timestamps UTC. `submissionId` on a user mutation is a stable caller-generated ID scoped to operation, actor and exact target. Identical replay returns the stored result before evaluating a now-stale precondition. A different payload for that identity conflicts. Native tool calls use their proven provider/session/turn/call identity for the same purpose. HTTP adapters verify browser/native grants, method, scope, strict shapes and body caps. ENTRY delegates its CLI and MCP commands to the same app services. The browser cannot assert a native tool identity or accepted GitLab result.

Use the [shared error contract](data-contracts.md). Malformed declarations return invalid_request. Wrong grants map to unauthorized/forbidden, inaccessible or absent targets to not_found, altered replay to idempotency_conflict and obsolete expected state to stale_revision. Use conflict for an applicable workflow whose proven binding or evidence no longer permits the transition. Use precondition_failed for an immutable content If-Match mismatch. Use payload_too_large for a metadata/rich-view byte budget, range_not_satisfiable for an invalid range, and unavailable for temporarily unreadable proof. Use the common structured error envelope and stable codes. Persist operational failure, retry and unknown delivery states even if a request disconnects. A read does not consume review work. HTTP status communicates admission or retrieval. Durable receipts supply evidence of later transitions.

Use typed application failures so callers choose a recovery action from the cause. `TargetMismatch` carries which authority boundary failed (review, lead, turn or call). `PreconditionChanged` carries the changed field and currently observed revision (head, disposition, monitor, report identity or native position). `IdempotencyConflict` identifies a reused ID with changed content. `EvidenceUnavailable` names the source and whether a fresh read is possible. `InvalidEvidence` indicates source hash, quote, completeness or scoped finding validation. `DeliveryUncertain` carries the existing submission ID for status lookup. The transport maps these to the common codes and sanitized messages. Unknown delivery after admission is a durable receipt the user can inspect. Compare-and-set failures keep the draft and return enough scoped identity for a fresh read.

## Verified actions and dispatch

A native declaration needs a currently working registered lead, matching provider native ID, run, review, turn, active call and **latest complete actual user input**. Match a known user submission to its persisted purpose. Reject an automatic/child prompt, hidden instruction, older entry, pending newer manual send or mismatched Claude companion entry. Re-read the native entry and current open MR after any async evidence read. For a cancel, verify the superseding user input. `comments` and `both` need 1–50 distinct targets keyed by (exact UTF-8 body SHA-256, discussionId or top-level). Identical reply text is valid in two different discussions. Each target needs its own matching GitLab note ID. `approval` and `cancel` carry zero comments. The native lead performs only the authorized remote work. A scoped automatic prompt may never declare new authority.

Drive `working → checking → completed | working | retry_wait | needs_input | cancelled`. Compare each note against the authenticated GitLab user's ID, requested digest, optional discussion and positioned head SHA. Store confirmed note IDs/time. Read approval for that exact authenticated user, independently of other configured reviewer identities or aggregate approval count. Conclusive absence requires complete current evidence. Keep unknown on partial reads, preserve prior confirmations, and show remaining targets. Keep original request identity, currently queued retry and last executed retry distinct. On superseding input, stop, closure or changed head, cancel only this authority and its known-unstarted continuation. An already sent operation can require readback. Another user's approval cannot complete ours.

Use the single HOST dispatcher. In one store transaction, save the action/retry and its exact outbox row, then wake HOST after commit. At claim and immediately before native submission, recheck current input/turn, permission, original SHA, live approval/notes, owner, capability, known completion and pending user work. A fresh read that already confirms the targets completes the action without sending. Continue only genuinely absent targets. At most three automatic sends for the same explicit request, a 10 s base wait and capped doubling for unknown evidence through 80 s. Hold and re-read unknown GitLab outcomes. An uncertain native send enters needs_input and is reconciled by exact submission ID. Inspect halted, uncancelled actions about once a minute so later confirmed success can close them. No automatic action continuation may steer a working turn. The native provider's final cross-client race remains visible through native receipts.

## Report acceptance and continuity

The accepted artifact belongs to the exact registered lead. Native tools stage one of the following handoffs. Metadata including bound follow-up coverage fits 128 KiB, allow 16 KiB HTTP overhead for routing. Keep file/response Markdown outside that limit. A native file payload specifies a canonical absolute path and SHA-256. Codex hashes the bytes before submission. Authenticated Claude can request server-side hashing for its actual file call. Restrict file access to the proven native execution and its authorized report source. Read one regular file descriptor, hash its raw bytes, decode valid UTF-8 without normalizing BOM, CRLF or trailing newline, check for replacement/mutation and verify again at capture. Response capture reads all chunks of the exact visible final result from a normally completed matching turn. Terminal output, ordinary replies, child results and text that resembles a receipt carry no report authority.

| Handoff | Acceptance |
|---|---|
| `final{source,revision,verdict,…}` | Revision is an exact full SHA or `{sha:null,reason}`. Verdict is approve/request_changes/blocked/not_specified. Verify canonical completed successful native tool call, proven origin/generation/turn/call/position and structured acknowledgement for the declaration. A final file can be accepted after a later turn failure when that exact tool succeeded with matching bytes. A response needs normal completion plus the full canonical result. Append immutable Markdown and advance current per-run receipt. Normal complete coverage records declared source and available target separately. |
| `unchanged{accepted:{receiptId,sha256},source,…}` | Require the current accepted identity and original source. Re-hash an accepted file. Require normal matching turn completion and successful native tool proof. Record the outcome and optional batch assessments against that accepted version. Preserve its report bytes, full-MR SHA and version count. |
| `needs_input{reason,…}` | Record actual reason, exact native turn and proof. Complete no finding assessment by implication. Keep prior accepted report and the open follow-up binding so a verified resumed turn can finish it. |

The repository determines the review method and can request its own report format. On launch or attachment ReviewQ gives both providers the [filled example](../../fixtures/contracts/report-handoff.json) for the [tool schema](../../contracts/report-handoff.schema.json). Field errors are returned before staging: schema and value errors first, then the ledger and batch checks, each list capped at 50 entries. Acceptance binds the configured project, checkout and GitLab identity. An unrelated board or automation edit can proceed while the receipt is pending.

`report_handoff` and `reviewq report handoff --file PATH` use the same generated input. `reviewq report example` prints the example. The repository's review instructions own the review method and the report; ReviewQ never asks the agent to change either. At the end of the review the agent makes one call that points at the finished report and adds the findings ledger described in [Findings ledger](#findings-ledger). The original Markdown is captured independently as exact bytes and every version renders through the same reader. [Input schema](../../contracts/report-handoff.schema.json) · [Example](../../fixtures/contracts/report-handoff.json)

`amendsReport` names the current accepted receipt and hash, omits `report`, and keeps the report's Markdown bytes, reviewed revision, verdict, coverage, findings and attention. An action turn can submit only an amendment. A correction is an ordinary final with the same reviewed revision.

A selected-thread submission adds thread assessments for its frozen batch. Its ledger lists new or rewritten findings and outcomes for re-assessed ones; untouched findings are carried. Earlier versions keep their own Markdown, findings and disposition history.

A carried finding keeps its last fields and details and links to the accepted receipt where its card was last authored. Source sections list the sections of the displayed version; earlier sections stay available from History.

### Findings ledger

ReviewQ owns finding state across versions and never infers it from prose. A final handoff other than an amendment carries a ledger:

- `report.findings` lists every finding the report raises, blocking and nonblocking, functional, security and quality. Each entry has a stable ID, title, severity, blocking status, consequence, and evidence or an explicit evidence gap, plus a location when applicable. `findings: []` means the review found nothing.
- `findingChanges` gives the outcome for a finding of the last accepted version that the agent re-assessed: `fixed`, `clarified_withdrawn` or `superseded` retire it, and `partly_addressed`, `still_present` or `unverified` keep it active. Outcomes are allowed in every phase. An outcome names a finding of the last accepted version; its checked revision is the handoff's reviewed SHA, or unknown with the revision. A retired ID cannot also be listed in `report.findings`.

IDs are the report's own (`F-01`) when it has them. The same concern keeps its ID across versions and a new concern takes the next unused ID.

Acceptance derives the next version by ID from the ledger, the report's level-three `F-` headings and the parent version:

| State | Rule |
|---|---|
| New | A ledger or heading ID that the parent's active set lacks |
| Updated | A parent ID with a ledger entry or a heading in this report, with or without a keeping outcome |
| Retired | A parent ID with a retiring outcome. It leaves the active set, counts and blocking, and its outcome stays on the version. |
| Carried | A parent ID with no retiring outcome, no ledger entry and no heading in this report. It stays active with its last fields, details and dispositions (a keeping outcome is recorded on the version), and records the receipt where its card was last authored. |

Fields come from the ledger, then the parent, then the authored heading. Anchors come from this report's heading when one exists; a carried finding keeps its earlier card's anchor when that card had one. A finding leaves the active set only through a retiring outcome. Counts are the size of the derived set. The reader draws every active finding that has no card in this report's text as a card in the same style after the authored cards; a carried card says so and opens its earlier card. The version summary counts these findings so the reader fetches them only when there are any. The user's dispositions overlay every version and always win.

These checks run while the tool call is open and return field errors the agent corrects in the same turn: the schema and its limits; outcome IDs and retired-versus-listed conflicts; a full review that leaves a finding of the last version without a ledger entry or outcome (the error names each missing ID and title); thread assessments, outcome discussion links and the reviewed SHA against the frozen batch; assessments without a selected-thread batch; an amendment that adds assessments or outcomes; a file whose bytes do not match the declared SHA-256; the stored size of the findings and their carried details; and, for a file report, any top-level level-three `F-` heading ID that is neither in the ledger nor carried. A final-message report has no text until the turn ends, so acceptance adds an unlisted heading ID as a finding instead of dropping it.

Acceptance rejects only for provenance: the workspace, base receipt, repository grant, settings authority or follow-up binding changed, the native proof or source digest doesn't match, or an amendment or unchanged result doesn't match the current accepted report. A disposition edit during the turn never rejects. The rejected bytes stay sealed with the reason and the last accepted version stays current.

On first admission, persist a service-issued receipt with the validated declaration, its server-bound scope and the verified (provider, native session, turn, call) identity. Compute `declarationSha256` once over the stored declaration bytes. A repeat of the same submitted declaration at that identity returns the stored acknowledgement. A changed declaration conflicts. The original native helper writes the acknowledgement as JSON to its captured result. If the reply is lost while the helper is running, it can recover that acknowledgement through handoff-status. Accept only after reading the successful original native call and matching its receipt and declaration digest. An echo from another call cannot complete it. Hold pending work while the source flushes and fence older source positions after rotation. Compare accepted receipt, report content hash, reviewed SHA or unknown reason and provenance at terminal readback.

## Capturing and revising accepted findings

Pin the base accepted receipt/hash at handoff. Capture report bytes, parse evidence and obtain native/refresh proofs outside SQLite. One conditional transaction checks that pin, native proof order, current handoff, run membership and frozen batch if present. It appends the version, CAS-advances the current pointer, saves outcomes and semantic attention identity, updates covered observations and inserts the due notification together. On conflict retain the captured unaccepted bytes, hash, reason, provenance and exact targets for reconciliation. Preserve the last accepted pointer and user decisions. Use a distinct short failure transaction. Reopen pending records on startup, reconcile by call identity, and publish invalidations/wake dispatch after commit. At most one correction request per active native turn, durably reserved before asking the same turn to correct missing/invalid metadata. Historical reconciliation is read-only against the host.

A report declares a full review, a private scoped check, or an amendment of the current accepted report.

| Form | Required continuity |
|---|---|
| Full review | Establish a new complete-MR baseline at the declared reviewed SHA, or retain the unknown reason. Every finding of the last accepted version has a ledger entry or an outcome. Registration's requested SHA, current head, Markdown recommendation and GitLab approval are independent facts. |
| Selected-thread final/unchanged | Bind to FOLLOW's exact batch, frozen submission, monitor generation, current or proven descendant native turn, baseline receipt/hash, checked source/target, every observation ID/version and lineage. One assessment per distinct selected discussion, covering that discussion's finding IDs; when this handoff retires every finding a discussion tracks, that discussion's assessment must be retiring; when it retires only some, the assessment must be retiring or `partly_addressed`. Untouched findings are carried. Only a full review can advance fullMrReviewedSha. |
| `amendsReport:{receiptId,sha256}` | Publication edit on the exact current report. Reuse its bytes, reviewed SHA, verdict, coverage, findings, conclusions and attentionReceiptId. Refresh GitLab outside the write transaction before capture. Append a version without another ready alert or completing an old batch. |

Recognize authored level-three F-number headings and explicit metadata on parsed Markdown blocks. Quoted or fenced words cannot change blocking. A finding outcome describes findingId, conclusion, reason and optional selected discussion IDs; its checked revision is the handoff's reviewed SHA. Each assessment supplies discussionId, conclusion, reason, findingIds and nextAction `review` or `waiting_author`. Enforce exact scope, complete unique assessments and stable identities. The user's latest disposition overlays the agent's blocking value on every version. For new versions record immutable per-finding disposition changes by run and revision. Bind an accepted report to its starting revision and freeze its final visible disposition revision when superseded, in the same commit as the new head. Current reads use the live revision. Historical reads reconstruct the last view of that receipt. Feedback locates the exact selected bytes/quote, including an older accepted version and Unicode. Both the rich Findings reader and the bounded source reader can supply quotes. Match the submitted quote exactly at the specified scalar offset and length against the named immutable version. A repeated literal quote requires its reference to identify a particular occurrence. For rendered text spanning markup or decoded entities, offer the exact underlying source for confirmation or reselection, preserving the draft and pinned version. Whole-report feedback remains available. Never manufacture a source range from synthetic headings, decorated labels or rendered HTML. The report viewing checkpoint, decision checkpoint, batch assessment viewing checkpoint and notification receipts advance independently.

Findings continues to show the accepted report when a later submission fails. Its History control identifies the failed update and opens the reason alongside the latest accepted report’s date and checked revision. A first failed submission leaves an explicit empty state. A failed receipt never advances the accepted version.

### Semantic indexing budget

Stream the complete native source to sealed storage in chunks of at most 64 KiB and hash every byte. Admit at most one full Markdown parse at a time per service and only for inputs up to 4 MiB of original UTF-8. Stage finding/section descriptors in bounded batches outside the final acceptance transaction. The parser takes a contiguous string and builds internal structures. Measure peak process memory on dense Markdown at the inclusive limit during REPORT. Source capture and readback remain available when the semantic parse limit is exceeded. [pulldown-cmark parser](https://docs.rs/pulldown-cmark/0.13.6/pulldown_cmark/struct.Parser.html)

Expose `semanticIndex=ready|source_only`. A verified independent full review beyond the limit may establish its authored source, revision and verdict; show Findings as source with a clear indexing status. Preserve existing dispositions against their original receipt. Counts and card-level operations come from the derived findings; source anchors require a complete index. A report that exceeds the parse limit is still accepted: the ledger supplies its findings and counts, and carried findings keep their earlier anchors. At the boundary exercise one full source and one scoped revision with the same fixture and check the prior pointer and chunked readback.

### Reading large reports

Compute byteLength in UTF-8, totalCodePoints in Unicode scalars, and physical line statistics when capturing an artifact, then persist with its receipt. Count LF boundaries (consume CRLF as one delimiter), exclude line terminators from maxLineBytes and do not count a trailing empty line after terminal LF. An empty artifact has zero lines. Return metadata first. Serve `view=markdown` only when byteLength ≤1 MiB, lineCount ≤10,000 and maxLineBytes ≤16 KiB. An over-budget explicit rich request returns payload_too_large with zero Markdown bytes. The summary already provides the metadata and immutable identity needed for section and download routes. Report acceptance still retains every verified byte.

For larger files, or on rich parser/AST-budget exhaustion, open a paged plain Markdown source reader pinned to the accepted version. Use at most 12,000 code points per page, choose `max(0,totalCodePoints-12000)` for Last, and provide previous, next and explicit offset navigation. Quote feedback can refer to global source offsets spanning visible source text. STORE supplies immutable chunks up to 64 KiB and indexed source offsets. End each short read snapshot before waiting on the network. Offer the complete original as a streamed native download without buffering the entire artifact into a JavaScript Blob or retaining it in browser cache. Keep summaries and notification invalidations free of report bodies.

## Selected-thread scheduling

Global default off, per-MR enabled/disabled overrides win. Monitor states are enabled, paused and archived. A complete authorized current MR read and stable reviewer identities are prerequisites. Choose latest accepted report's lead, or the sole registered lead when no report exists. Multiple possible leads without reports require a selection. Preserve assignment across navigation and new reports. Initial enrollment uses actual published notes by the configured reviewer identities. Exclusions follow original note IDs if GitLab promotes an individual comment into a discussion. Require a unique identity match. A matching filename, similar body, resolved badge or private finding cannot establish a thread.

| Event or decision | Recorded work |
|---|---|

For example, suppose a monitor links original note 91 in discussion D7 to finding F-01. A reply creates observation O4 at discussion version 3. The accepted baseline also contains F-02 under an explicit nonblocking disposition. A native check with no Markdown changes can send the following semantic assessment against its current accepted report.

```json
{"assessments":[{"discussionId":"D7","conclusion":"still_present","reason":"The selected guard still permits an empty list. The original note already asks for that guard.","findingIds":["F-01"],"nextAction":"waiting_author"}]}
```

The server binds O4/version 3 and the checked source SHA from the frozen batch. The user helper never supplies an invented observation or turn. That result adds one completed batch and zero report versions. F-02 remains an outstanding card with its earlier checked revision and disposition. A later reply creating O5 remains eligible even if it arrives before the first result is viewed.

Every automatic delivery checks pending questions/permissions, busy related sessions, earlier pending handoff, manual send/unknown receipt, provider readiness, preserved native model/effort and current eligibility at claim and send. Native model/permission recovery uses HOST's same outbox and only legal capacity evidence. It can extend an existing batch to the exact acknowledged resumed turn or an unambiguous same-session Codex root turn in the original executing lineage. A prior permission to publish never broadens a private check. Threads are evidence. The prompt authorizes reading and drafting only. Closing the drawer, viewing a result or losing the HTTP response cannot reauthorize a send.
